## 0. 结论先行

### 三条核心判断

**判断一：不要从零写，选 CrossMux 作为 fork 基线。**
原因不是 CrossMux 的阅读体验最好，而是**只有它已经把这台机器的 BSP 做完并合进了主干**——1216×684 并行 EPD 驱动、16 级灰度、CST836U 触摸 + 屏幕下方三个电容实体键、CW32L010 PMU（电量/RTC/深度睡眠）、SC7A20H 加速度计、1-bit SDMMC、双槽 A/B OTA。这些是"让墨水屏亮起来"的部分，工作量占整个固件的 50% 以上，而 `crossmux` 已经有可直接编译的 `readpico` 环境。从零开始做 BSP 是纯粹的重复劳动和风险。

**判断二："纯阅读"应该被当作一次 Flash 预算腾挪，而不只是删功能。**
Read Pico 的 A/B OTA 槽只有 **6,553,600 B**（6.25 MiB），当前 CrossMux ReadPico 固件已经用到 **6,133,808 B（93.6%）**，只剩 **419,792 B**，**已经低于项目自己要求的 512 KiB 余量门槛**。而用户真正每天会遇到的痛点恰恰是**内置中文字库不足**——`chinese-build.md` 白纸黑字写明：内置只有 8/10/12pt 的 **3,517 字**常用字集，而 **14/16/18pt 只有 i18n 子集（仅 802 字，只够渲染界面文字）**，读正文**必须**依赖 SD 卡 `.cpfont`，否则生僻字显示成 `□`，还会弹"下载完整字库"引导。相反，游戏（五子棋/数独/象棋/扫雷/2048/推箱子/计算器/木鱼/丑头像）、AirPage 相册（含 MQTT 常连）、老黄历、成就系统、BLE、**33 国语言包**这些"非阅读"的东西占了大量 Flash。
**把非阅读功能砍掉，换来的空间正好用来把完整中文字库内嵌进去**（目标：GB2312 一二级 6,763 字 × **20pt 主档位 + 14pt + 12pt**）。这才是"纯阅读固件"的正当性所在——不是"少了功能"，而是"把资源全押在阅读上"。
> 一个具体例子：`璟` 这个字被 `chinese-build.md` 明确列为"**故意不包含**"。用户书架里有《哈利波特全集》《那不勒斯四部曲》这类人名地名密集的书——**这种字一定会遇到，而且一遇到就是整串标题换成别的字体**（上游的回退粒度是"整串"而非"逐字"）。

**判断三：界面语言学微信读书的"克制"，但不要学它的"层级"——而且要对齐它的**墨水屏版**，不是手机版。**
本次调研最关键的发现是：**微信读书官方自己已经做过一次极简化**。官方「墨水屏版」把整个 App 压成**一块主屏**（顶部搜索 / 中间书架 / 底部榜单），**从 4 个 Tab 收敛为 1 屏**，砍掉听书等高级功能，"除书籍封面外整体以黑白色为主"，没有动画、没有弹窗、没有推送（[IT之家](https://www.163.com/dy/article/F1ALP3BK0511B8LM.html)、[BOOX 实机体验](https://www.163.com/dy/article/F19AP0NJ0518J9AH.html)）。**官方替我们做完了"哪些该砍"的决策。**
值得抄的三条经核实的原则是：**① 阅读页默认全屏无干扰，点一下中间才浮出 UI；② 底部一条工具栏解决所有阅读操作（官方确证是 4 键：目录/进度/阅读背景/字体）；③ 用页码而非百分比、章节名做书眉——即"纸书隐喻而非 App 隐喻"**。
不值得抄的是手机版的多 Tab 信息流、书城、社交圈子、勋章与海报分享——**这些在官方墨水屏版里已经被删掉了**。在 684 px 宽、单色、刷新一次 200–400 ms 的屏幕上，层级越浅越好。**已确认取消 Tab 导航**，纸读只用**两个层级**：首页 ⇄ 阅读页，其余全部是阅读页上的浮层。

**判断四（已确认）：微信读书不该进这台设备。**
CrossMux 的微信读书客户端确实能"扫码登录、书架同步、EPUB 下载、进度双向同步"，是真功能。但它带来的是：**一个不校验证书与主机名的 TLS 客户端**（上游自己在文档里写明 `setInsecure()`）、**一个随时可能变更的非官方 Web 协议**、Cookie 与会话凭据落盘、以及一整套网络内存开销。而你的真实需求是"**纯阅读**"——书从电脑传进去，然后离线读几周。
**已确认删除**。收益有三：**省 200–350 KB Flash**（正好抵消 20pt 字库的增量）、**消掉方案里唯一的非官方协议与最主要安全风险面**、**让固件从"必须联网"变成"完全离线可用"**。WiFi 只剩传书一个用途。



### 一句话方案

### 已确认的八项产品决策（用户 2026-10-06 拍板）

| # | 决策 | 对方案的影响 |
|---|---|---|
| **1** | **正文默认 20pt** | 版式重算（每页约 22 行 / 506 字）；**内嵌字库主档位改为 20pt**，体积比 16pt 方案上升约 1.5× |
| **2** | **取消 Tab 导航** | 首页做成单页；原「书库/统计/设置」→ 决策 7 调整为 **最近阅读 / 书库 / 设置** 三个下钻入口，**正文多 2–3 行** |
| **3** | **不保留微信读书** | **删掉整个 `weread/` 模块**（TLS + Cookie + 非官方协议 + `setInsecure` 证书校验风险）。**回收 200–350 KB**，正好抵消决策 1 带来的字库增量；同时**消除本方案唯一的非官方协议依赖与最主要的安全风险面** |
| **4** | **要做划线 / 批注** | 由"只读书签"升级为**段落级划线 + 批注**。v1 采用**下划线式**（1-bit 上优于底色高亮），并提供**笔记导出到 SD**（见 §6.8） |
| **5** | **要"拾取唤醒"**（SC7A20H） | 需绕过 `Imu` 抽象层直接写寄存器（`CTRL3` + `AOI1`/`HPIS1`），并把 GPIO1 配成深睡唤醒源；有误唤醒风险，做成**可校准、默认关闭**的开关（见 §6.8） |
| **6** | **不做 USB 挂载，也不做 WiFi 传书；传书仅靠人为拷贝** | ✅ 这一刀同时砍掉**两项**最重的东西：USB MSC（要放弃 `firmware_tuned` 的 32–37 KB 堆回收）与**整个 WiFi/TLS/HTTP 协议栈**。固件从"基本离线"变成**完全无网络代码**，预算反而从"勉强达标"变成"宽裕"（见 §6.9） |
| **7** | **UI 仅三项：最近阅读 / 书库 / 设置** | 入口从五个减到三个；**「阅读统计」不再是独立页面**，它只剩一个数字，并入首页底部（§7.5） |
| **8** | **时间和日期彻底删除，统计也不按天** | 删掉 PMU RTC 日期读取、校时设置、页脚时钟、`dayOrdinal`、连续天数、7 天/30 天热力图、日均、官方时长分档。**统计只剩三个纯累加指标**（§7.5） |

> **决策 8 是"减法链条"的终点，也是收益最大的一步。** 它砍掉的不只是 UI：**PMU RTC 的日期读取路径、跨日切分会话的逻辑、连续天数算法、热力图渲染整条链路全部消失**。根本原因是——**阅读统计从来不需要"绝对时间"**，只需要两个累加器（总毫秒 + 会话次数）。原设计要 RTC 只是为了让"按天分组"这个 UI 形式成立；**去掉形式，时间依赖就整条消失**。
>
> **决策 3 的一个额外好处**：不保留微信读书后，纸读**不需要联网才能读书**。
> **而决策 6 把这一点推到底**：既然传书只靠人为拷贝，WiFi 就没有任何用途了——**整个网络栈可以删掉**。一台离线阅读器不该带一个不校验证书的 TLS 客户端，也不该为每月几次的传书常驻一套 HTTP 服务器。

### 一句话方案

> 以 `crossmux` 的 `readpico` 环境为基线（MIT；BSP 已合主干、有桌面模拟器），**删掉全部非阅读活动、砍掉微信读书模块、把 33 国语言收敛到 zh-CN + en**，回收约 **1.2 MB** Flash，用于**内嵌 GB2312 一二级（6,763 字）× 20pt + 12/14pt 完整中文字库（正文默认 20pt）**，并修掉实测到的**中文文件名乱码（B1，删网络后升级为阻塞级）**与**CSS 内存不足静默降级（B2）**；补齐 **段落级划线/批注**（§6.8）与 **拾取唤醒**（§6.8），并**删掉 USB 挂载与全部 WiFi 代码**——传书仅靠人为拷贝到 SD 卡，OTA 改为从 SD 卡本地更新（§6.9）；UI 对齐微信读书**墨水屏版**的极简思路——"**全屏正文零装饰** + 点按浮出 4 键工具栏 + **页码页脚**"，**取消 Tab 导航 + UI 仅三项入口（最近阅读/书库/设置）+ 彻底删除时间与按天统计**，全程只保留**首页与阅读页两个层级**。

### 1.2 一个必须澄清的技术点：ReadPico 的显示路径

早期资料（以及仓库里尚未清理的注释）会说 ReadPico 走 **M5GFX / LovyanGFX 的 i80 总线**。**这是过时信息。** 查证当前的 `platformio.ini`（第 968–1059 行）：

```ini
[readpico_hardware]
  EpdiyLcd=symlink://freeink-sdk/libs/display/EpdiyLcd     # ← epdiy 的 LCD 输出路径
  ; M5GFX is deliberately NOT here: leaving it in would ...  # ← 明确不再需要 M5GFX
  -DFREEINK_DEVICE_READPICO=1
  -DFREEINK_EPDIY_LCD_CONFIG=readPicoEpdiyConfig
```

即：**ReadPico 用的是 epdiy 的 `EpdiyLcd` 后端（LCD_CAM + GDMA + RMT 直驱裸并口面板），M5GFX 已被刻意移除。** 早先的 Lovyan i80 实验和转换后波形都已删除。
**对本设计的影响**：修改显示/波形层意味着要动 `freeink-sdk/libs/display/EpdiyLcd/`（内含上游 epdiy 的裁剪副本）；**纸读 v1 不碰这一层**，只在其上做刷新策略调度（§6.6）。

### 1.3 三个对 UI 设计有决定性影响的硬件约束

**约束 A：触摸区比屏幕高，实体键在屏幕外面。**
触摸面板的原始坐标是 684×1216 的**玻璃面**，但三个电容键区落在 `y > 1300`，也就是**屏幕内容区之外**。这意味着：
- 触摸坐标必须先分流：`y ≤ 1215` → 屏幕内容点击；`y > 1300` → 实体键。
- 三个键的中心 x = 80 / 240 / 400，间距 160 px。这是"上一页 / 确认 / 下一页"的天然物理映射。
- **设计含义**：微信读书靠"点屏幕左/中/右三区"翻页，这台机器**既有**屏幕三区点击、**又有**屏幕外的三个实体键——两者应该都支持并保持一致（左键=上一页，中键=呼出菜单/确认，右键=下一页）。

**约束 B：Flash 只剩 419 KB 或 486 KB。**
`high-dpi-ui-profile.md` 记录：正常固件 6,133,808 B / 槽 6,553,600 B（余 419,792 B）；Nightly 6,066,720 B（余 486,880 B）。而 CrossMux 自己的发布门槛要求**至少保留 512 KiB 余量**——**当前 ReadPico 构建已经不达标**。任何"再加一个功能"的想法都必须先想办法省空间。

**约束 C：PSRAM 很富裕，内部 RAM 极度紧张。**
PSRAM 空闲 5–6 MB，但内部 RAM 空闲常常只有 30–45 KB、最大连续块 25–31 KB。已记录的后果：
- "CSS parsing was skipped because the parser required 65,536 bytes"（CSS 解析因需 64 KB 连续内存而被跳过，样式丢失）。
- 分页/渲染路径必须复用缓冲区，不能随手 malloc。
- **设计含义**：所有大缓冲（帧缓冲、字库索引、图片解码工作区）走 PSRAM；所有小对象避免碎片化；**不要引入新的长生命周期堆分配**。

### 1.4 排版可用空间推算（684×1216 竖屏，**正文基准 20pt**）

> **已定决策：正文默认 20pt**（用户指定）。本节所有版式计算以此为基准。

```
可绘制高度 = 1216 - 5(上) - 8(下) = 1203 px

版式分区（全部按 20pt 推导）
  章节名行（书眉）      20pt × 1.6 ≈ 32 px + 上下留白 16 px = 48 px
  页脚（页码 + 信息槽） 20pt × 0.7 ≈ 14pt → 行高 24 px + 留白 10 px = 34 px
  正文字区高度         = 1203 - 48 - 34 = 1121 px

正文字号与行高（行高 = 1.6 × 字号）
  行高 50 px  → 1121 / 50 = 22.4  →  每页 22 行
  行高 54 px  → 1121 / 54 = 20.7  →  每页 20 行（行距调到 1.8× 时）

每行字数
  正文宽 = 684 - 32(左) - 32(右) = 620 px
  20pt 全角字宽 ≈ 20 × (96/72) = 26.7 px
  620 / 26.7 ≈ 23.2  →  每行约 23 个汉字（避头尾压缩后实际 23–24 字）

单页密度 ≈ 22 行 × 23 字 ≈ 506 字/页
```

**与既有实测的交叉验证**：CrossMux 文档记录 12pt 在 31 px 边距下每页 32–33 行（正文区 1119–1126 px），回算 12pt 行高 ≈ 1121/32.5 ≈ 34.5 px（≈2.87 px/pt）。而 20pt 按 1.6 倍行高为 50 px（2.5 px/pt）——**20pt 的相对行高比 12pt 更紧**，所以 22 行是保守估计，实测可能在 22–24 行。**以阶段 4 的模拟器/真机截图为准。**

**为什么默认 20pt 是合理的**
- 用户当前就是 `fontSize:22`，而且 `fonts/` 下 4 套字族都装了 20pt 与 22pt 的 `.cpfont`——**他一直在用这个尺寸，只是 SD 字库在支撑它**。
- 684 × 1216 在 4.7 英寸上是 **≈297 PPI**，与主流 6 英寸阅读器同级。20pt 在此密度下约 1.9 mm 字高，是**明显偏大但舒适**的中文阅读尺寸。
- **代价**：每页约 22 行 / 506 字，比 16pt（27 行）少约 19%，翻页更频繁。**这是用户明确选择的取舍**，方案照此执行。

**由此产生的一个连带约束（很重要）**
默认字号定为 20pt，意味着**内嵌字库的主档位必须是 20pt**，而 20pt 每字位图面积约为 16pt 的 **(20/16)² ≈ 1.56 倍**。字库体积会因此上升——**这正是"顺带砍掉微信读书"能救回来的地方**（见 §6.4 的预算重算）。


### 1.5 一个必须告知用户的硬件级稳定性代价

`read-pico-reader` 作者在 `sdkconfig.defaults` 注释中记录了一条**硬件级**问题，纸读无法修复，只能规避：

> 120 MHz 下 Flash 与 PSRAM 共用时钟域，PSRAM 想跑 120 MHz 则 Flash 必须同步。**上电后约 20 ℃ 的温漂会让 PSRAM 随机出错**，而 ESP-IDF 的温度补偿只验证过 flash vendor `0xC8` / `0x20`。本机是 Zbit（vendor `0x5E`），**开启温度补偿会在 `do_system_init_fn` 直接 abort——因此必须关闭，也就等于没有这层保护。**

**含义**：这台机器在温度变化较大的场景（冬天从室外带进屋、夏天车内）可能发生随机崩溃或数据损坏。
**纸读的应对（v1 必做）**：
1. **持久化写入全部走原子路径**：`.tmp` + rename（CrossMux 的 `settings.json`/`state.json` 已是这个模式，沿用并扩展到 `bookmarks/` 与统计文件）。
2. **阅读进度写入频率限制**：不要每翻一页写一次；改为"每 10 页或每 30 秒"写一次 + 退出阅读页时强制写一次。
3. **写后校验**：进度文件写入后立刻读回比对（CrossMux 的微信读书同步已有"read-back 验证"先例）。
4. **崩溃后自愈**：启动时若发现某书 `progress.bin` 损坏（长度/CRC 不符），回退到上一份 `.bak`，最差情况退回章首而不是全书丢失。
5. **设置页"关于"里如实说明**：这是硬件限制而非固件缺陷，避免用户误判为固件不稳定。

> 这一条恰好强化了"纯阅读"的合理性：**功能越少，写入越少，暴露在温漂风险下的机会越少。**

#### 阅读体验的**劣势**

1. **内置中文字库对正文不够用**（最致命）。`chinese-build.md` 原文：*"Offline reader fallback is 12pt only"*、*"Rare characters render as □ in reader at SMALL until an SD font is installed"*、*"for example, 璟 is intentionally absent"*。且 14/16/18pt 是 **i18n 子集（仅 802 字）**，只够渲染界面文字，**完全不够读正文**。叠加"按整串回退"的机制，一个缺字会让整行标题都换成 SD 字体。
2. **CSS 解析会被内存不足吞掉**（实测 B2）。需要 64 KB 连续内存，失败就静默降级。
3. **中文文件名乱码**（实测 B1）。
4. **横屏页脚裁切**（实测 B3）。
5. **无划线/批注**。只有书签。微信读书的核心能力之一缺失，且上游 `SCOPE` 未把它列入计划。
6. **重命名书会丢进度**。每本书的缓存目录名是 `std::hash(路径)`，改文件名即重新算 hash，旧 `progress.bin` 找不到。（TXT/Markdown 有专门的迁移处理，EPUB 没有。）
7. **Flash 已到 93.6%**，ReadPico 构建**不满足项目自己的 512 KiB 余量门槛**；`CONFIG_COMPILER_OPTIMIZATION_PERF` 因怕溢出而**不敢开**（停在 `-Os`）。
8. **功能过载**：游戏（数独/五子棋/象棋/扫雷/2048/推箱子/像素开关/计算器/电子木鱼/丑头像）、AirPage 相册（MQTT 联网）、老黄历、阅读成就、头像系统、BLE 翻页器。对一个"纯阅读"设备，这些是**噪声**，而且是**Flash 的直接竞争者**。
9. **ReadPico 目标尚未硬件验收**：README 明确写 *"This target is build-only in this round... no hardware acceptance has been recorded yet"*；社区文档也记录了页脚遮挡、长期残影、波形/电气行为、≥3 次睡眠唤醒等未决项，且**明确声明"模拟器/软件检查不能关闭这些项"**。
10. **维护成本高**：作为"fork 的 fork"，合并上游 CrossPoint 是**有文档记录的持续负担**（`upstream-merge-policy.md` + 一份 124 KB 的上游同步评审文档）；阅读统计套件还维护在**另一个仓库**里、只做单向同步。


#### 选它的理由

- **唯一**已经把 ReadPico 全套 BSP 合进主干的公开项目。
- **唯一**同时具备"原生 16 级灰度 + 微信读书双向同步 + CJK 深度优化"。
- MIT 许可，8,215 star 的上游生态，社区活跃（天天有提交）。
- 已有 `simulator_readpico` 桌面模拟器（684×1216 竖屏、`{5,5,8,5}` insets、鼠标模拟三键），**可以不开真机就开发 UI**。这一点对迭代速度是决定性的。

#### 优劣势判断

**优势**
- **最贴近官方硬件**：基于 MindReset 官方 demo，板级细节（PMU、波形、VCOM）最可信。
- **覆盖最完整**：`components/` 下有 `cst836u`、`sy7636a`、`fca9555`、`sc7a20h`、`read_pico_pmu`、`e0470_epaper_waveform`、`epdiy`——等于**自带完整厂商 BSP**。
- **排版认真做了中文**：整字列居中 + 标点避头尾 + 首行缩进，这三条是中文排版的真问题，CrossPoint 系未必处理得好。
- **翻页波形专门调过**（`continuous_du` / `e0470_page_turn`），残影控制可能有优势。
- **在线刷机 + 卡内 OTA + 自动回滚**，工程完成度高。
- **开发速度极快**：2026-10-03 建仓，10-06 一天内推了 rc79→rc82。
- 提供 `AGENTS.md`、`docs/HANDOFF.md`、`ONBOARDING.md` —— **是 AI 辅助开发的产物**，对后续由 AI 维护的固件反而友好。

**劣势**
- **只有 12 star、3 fork、无 release 记录、无 issue**：几乎零社区，**单点依赖**（一个人 + AI）。仓库建立至今**仅 3 天**（2026-10-03 创建），却在 9 天内推到 rc82。
- **许可证复杂**：主体 Apache-2.0，但 **epdiy 是 LGPL-3.0-or-later**（明确写在 `THIRD_PARTY_NOTICES.md`）。LGPL 在固件里意味着**必须提供该组件的源码与替换方式**——对分发是约束。**这是纸读不采用该路径的实质原因之一**（纸读用 freeink-sdk 的 `EpdiyLcd`，避开这一约束）。
- 格式只支持 **EPUB/TXT**。`book_open()` 对其它扩展名一律返回 `ESP_ERR_NOT_SUPPORTED`。**无 XTC/XTCH、无注音、无断字、无词典、无 KOReader/OPDS/WebDAV/Calibre 同步**。
- **无笔记/划线能力**（微信读书的核心能力之一）。
- 微信读书**只下载不上传进度**，且作者自标"真实账号登录/下载仍需实机验证"；rc19 版本曾一度**移除**微读入口与在线阅读模块。
- **无桌面模拟器**。有 `tools/run_display_host_test.sh` 宿主渲染/排版回归测试，但**没有可交互的 SDL 模拟器** → UI 迭代必须上真机，慢。
- **已承认的硬件级稳定性代价**：PSRAM 温漂（约 20 ℃）可致随机出错，且温度补偿**必须关闭**（Zbit flash 不在 IDF 验证表内，开启会在 `do_system_init_fn` abort）。这是可导致随机崩溃/数据损坏的实质风险（详见 §1.5）。

### 3.5 阅读维度的"利弊"提炼（回答用户的问题）

**CrossMux 在阅读上的利**
引擎能力天花板最高：EPUB2/3 + CSS + 自适应表格 + 断字 + 字距 + **CJK 注音** + 脚注 + StarDict 词典 + 阅读参考线 + 专注阅读 + 自动翻页 + 16 级灰度 + TTF 直读。**它是四个方案里唯一有"词典"和"注音"的**——对中文读者这两项价值很高。微信读书同步也是唯一双向的。

**CrossMux 在阅读上的弊**
① 内置字库在默认 14pt 下**不可用**（只有 802 个 i18n 字），必须自备 SD 字库；② CSS 解析会被内存不足静默跳过；③ 中文文件名乱码；④ 横屏页脚裁切；⑤ Flash 见底导致**不敢开 -O2**、**不能再加功能**；⑥ 功能过载把"阅读优先"的口号稀释了；⑦ ReadPico 目标**从未硬件验收**。

**read-pico-reader 在阅读上的利**
排版细节最懂中文（整字列居中、标点避头尾、首行缩进三档）；翻页残影有专门波形组件；基于官方 demo，板级可信度最高；工程完整（在线刷机/卡内 OTA/自动回滚/设置备份）；开发迭代极快。

**read-pico-reader 在阅读上的弊**
格式只 EPUB/TXT；**无笔记划线、无词典、无注音、无断字**；微信读书**只下不上**进度；无桌面模拟器所以 UI 迭代慢；**12 star 单人项目 + 建仓 3 天**，长期可持续性风险最高；LGPL 组件对分发有约束。

**RickyOS 在阅读上的利**
信息架构最贴合"阅读回到主角"：继续阅读优先的首页、书库三态分组、底部导航、存储与生活工具分区——**UI 设计上最值得借鉴的一版**。安装与更新体验最好，且尊重 SD 卡数据。

**RickyOS 在阅读上的弊**
闭源，**无法作为固件基线**（这是硬伤）；阅读能力无任何公开技术文档，格式/字库/注记/同步全部不可评估；无法审阅排版与省电实现。

### 4.2 发现：**这台设备当前跑的很可能就是 CrossMux（带 inx UI）**

证据链：

1. `.crosspoint/` 目录里有 `weread/`（**只有 CrossMux 系有微信读书客户端**；上游 CrossPoint README 完全没提微信读书）。
2. `achievements.json`（4,716 B）—— CrossMux 的"阅读成就"功能。
3. `AirPage/` 目录 + `.crosspoint/airpage_device_id` —— **AirPage 是 CrossMux 的独有功能**（扫码上传图片 + MQTT 前台实时投递）。
4. `gomoku.bin` / `gomoku_stats.bin` —— CrossMux 的"五子棋"应用存档。
5. `settings.json` 含 `inxRecentLayout` / `inxLibraryLayout` / `inxAppsLayout` / `inxTabPosition` —— **这是 inx fork 的 Tab 布局键**，而 CrossMux README 明确致谢 inx，并且 `high-dpi-ui-profile.md` 大量描述 INX 首屏几何（"INX home derives its tabs, five book layouts..."）。
6. `appsCatalogVersion` / `hiddenAppsMask` / `buddyClaimed` —— CrossMux 的应用目录与"丑头像"系统。
7. `contentProfile:1` + `langSku:"cn"` —— 正是 CrossMux 的"中国内容档"机制。
8. `sdFontFlashPreload` —— CrossMux 的 SD 字体 Flash 预载路径。

**这个发现改变了整个设计的起点**：用户不是在"从原厂固件出发考虑换一个"，而是**已经在用 CrossMux 的前沿版本，现在想要一个更纯粹的版本**。这带来两个直接结论：

- **迁移成本极低**：新固件只要能读 `.crosspoint/settings.json`、`reading_stats.json`、`epub_*/progress.bin`，用户**不用重新配置、不会丢进度**。
- **必须解释"为什么再做一个"**：CrossMux 已经很能读了。答案只能是——**砍掉非阅读负担，把省下的 Flash 全部换成"开箱即用的中文阅读质量"**（完整内嵌字库 + 修复乱码 + 修复横屏页脚 + 敢开 -O2）。

## 5. 微信读书 UI 设计语言拆解与其电子墨水屏适配

> **本节资料来源与可信度说明**：以下内容基于微信读书**官方帮助页**（`weread.qq.com` 的"如何设置阅读界面的背景和字体"、"如何查看目录和全文搜索"）、**腾讯官方开放的 WeChatReading API 契约**（`github.com/Tencent/WeChatReading/skills/`）、以及多篇产品拆解。
> 凡属推断或未能核实的部分，均以 **[推断]** / **[未证实]** 显式标注。**微信读书未公开其字号档位、行高倍数与边距数值**——网上流传的具体数字都是猜测，本方案给出的数值是**为 684×1216 墨水屏重新设计的建议值**，不是官方数值的引用。

### 5.0 最重要的一个认知：微信读书**已经**为墨水屏做过一次极简化

这是本次调研中最有价值的发现，它直接改变了本设计的方法论：

> 官方 **微信读书墨水屏版（26.2 MB）** 把整个 App 压缩成**一块主屏**：顶部图书搜索框，中间书架，底部各榜单，"除此以外基本没有多余的设置，系统非常纯净，操作也极其简单"。
> 并且："**除书籍封面外 APP 整体也以黑白色为主**"，砍掉听书等高级功能，从 4 个 Tab 收敛为 **1 屏**。
> — [IT之家 / BOOX 适配报道](https://www.163.com/dy/article/F1ALP3BK0511B8LM.html)、[TechWeb 上线报道](https://m.techweb.com.cn/article/2019-12-24/2770686.shtml)

**结论：纸读不应该对着"手机版微信读书"设计，而应该对着"墨水屏版"设计。** 手机版的多 Tab 信息流、书城推荐、社交圈子、勋章、海报分享，在墨水屏版里**已经被官方自己删掉了**。官方替我们做完了"哪些该砍"的决策。

同时要注意墨水屏版的一个反直觉细节：它在**底部右侧提供了屏幕上的「上/下」翻页按钮**，以避免依赖滑动手势（[BOOX 实机体验](https://www.163.com/dy/article/F19AP0NJ0518J9AH.html)）。这与本机"触摸 + 屏外三电容键"的硬件特性高度契合——**墨水屏用户不排斥"看得见的翻页控件"**。

### 5.1 信息架构：书架与阅读是两种不同的东西

这是整个微信读书结构上的**核心区分**，也是纸读最该继承的一点：

| | **书架** | **阅读页** |
|---|---|---|
| 本质 | 一个 **Tab**，常驻底部导航 | **全屏模态推入**，无底部导航 |
| 界面装饰 | 顶部搜索 + `+` + 书架/书单切换；底部 Tab 栏 | **默认完全无装饰**，只有正文 |
| 翻页方式 | 滚动/网格 | 分页（横向）或纵向滚动 |
| 退出方式 | 切 Tab | 返回手势/按钮 → 回到书架 |
| 首要任务 | 找书、管路书、挑书 | 零干扰地读 |

**手机版微信读书的底部 Tab**（历史版本有"发现/书架/故事/我的"与"阅读/书架/发现/我"两种）。注意一个**命名陷阱**：第一个 Tab 在 V6 叫「阅读」，但它其实是**发现/首页信息流**，真正的读书画布是**全屏推入的模态页**，不是 Tab。纸读不要复制这个名字。

**微信读书阅读页的正文章节顺序**（值得模仿的"纸书感"）：**扉页 → 版权信息/寄语/导语 → 正文 → 读完页**。其中"读完页"显示读完日期、本书阅读时长、"这是你读完的第 X 本书"，并可生成分享图。

### 5.2 阅读页布局：章节名在**顶部**，页码在**右下**，想法数在**左下**

**默认状态是一行装饰都没有的。** 官方帮助页与产品拆解一致描述为：

- **顶部**：章节信息（running head，像纸书的书眉）
- **左下角**：**当前页的想法数量**（"让人感觉不是一个人在读书"）
- **右下角**：**当前页数 / 总页数**，例如 `128/560`

```
┌────────────────────────────────────────┐
│  第三章  论人类不平等的起源   ← 顶部：章节信息（书眉）
│                                        │
│   正文正文正文正文正文正文正文正文…      │
│   正文正文正文正文正文正文正文正文…      │
│   正文正文正文正文正文正文正文正文…      │
│   正文正文正文正文正文正文正文正文…      │
│   正文正文正文正文正文正文正文正文…      │
│                                        │
│  💬 12 个想法              128/560  ← 底部：想法数 | 页码
└────────────────────────────────────────┘
```

#### ⚠️ 两处必须纠正的常见误传

**误传一："底部右角是全书百分比。"**
**不是。** 右下角是**页码**。2024 年 10 月有用户在豆瓣明确询问"右下角页码怎么改成百分比"，得到的回答是**没有这个选项**（[豆瓣讨论](https://www.douban.com/group/topic/312707649/)）。
**对墨水屏的意义**：**页码比百分比更好**——页码是离散的、锐利的、纸书原生的，且和正文字体同源；百分比会引入无谓的数字位宽与刷新。**纸读的阅读页页脚主指标用页码，不用百分比。**（百分比出现在**书架封面徽章**与**统计页**，这与官方是一致的分离。）

**误传二："底部工具栏有 5 个或 6 个按钮。"**
**官方帮助页写得很明确：4 个。**

> 在阅读界面，点击屏幕中间（大概竖屏 1/3 位置），会出现工具栏。所有阅读界面相关的设置都可在此完成。底部四个按钮分别为「目录」「进度」「阅读背景」「字体」
> — [微信读书官方帮助](https://weread.qq.com/wrpage/app/help/detail/qReadingBgAndFront)

网上流传的 5/6/8 键版本是**版本漂移**（产品拆解里出现的"笔记/夜间/设置"是被描述为**功能组**，不是一排按钮）。**以 4 键为基准。**

### 5.3 点按后出现的工具栏

**触发**：点屏幕中间（官方原文："大概竖屏 1/3 位置"）。

**底部 4 键（官方，最高可信度）**

| # | 名称 | 功能 |
|---|---|---|
| 1 | **目录** | 章节目录；**目录面板顶部带搜索框**（"在目录顶部搜索框输入关键词可搜索本书相关内容"） |
| 2 | **进度** | **可拖拽滑块** + 章节导航 |
| 3 | **阅读背景** | 背景色 + 夜间模式 |
| 4 | **字体** | 字体族 + 字号 |

**顶部栏**（同时浮现）承载次级操作：**听书（TTS）、更多（自动阅读 / 下载到本地 / 私密阅读 / 隐藏想法）、分享**，外加"加入书架"的强提示。
**想法输入框固定在底部**，方便随时点击输入。

**关键设计原则（官方拆解原文）**：

> 调节阅读进度、自动阅读速度、页面亮度时，采取**拖拽进度条（而不是定制分级）**的形式，使读者找到更匹配的"度"，打造个性化阅读

**这条原则在墨水屏上必须换机制但保留精神**——见 §5.7。

### 5.4 排版与版式

#### 官方确认的只有一句话

> 在下方的工具栏里，点击第四个按钮「A」，可以设置阅读字体和字号
> — [官方帮助](https://weread.qq.com/wrpage/app/help/detail/qReadingBgAndFront)

官方把工具栏描述为涵盖*"所有阅读界面相关的设置"*；产品拆解进一步列出设置面为：**阅读进度、自动阅读、阅读背景、页面亮度、字体大小、边行距、字体**——即**字号、行距、边距是三个独立控件，且都是滑块而非分级**。

#### 【未证实】官方的字号档位/行高倍数/边距数值

**微信读书没有公开这些数值。** 任何在网上看到的"微读字号是 16/18/20px"之类都是猜测。
以下是为本机 684×1216 重新设计的**建议值**：

| 参数 | 纸读建议值 | 理由 |
|---|---|---|
| 正文字号 | **16pt 默认**，可选 12/14/16/18/20/22/24pt | 684 px 宽下 16pt 每行约 38 字；用户当前用 22（偏大） |
| 行高 | **1.6×**，可选 1.4 / 1.6 / 1.8 / 2.0 | 中文需要比拉丁文更大的行距；微读观感偏"疏朗" |
| 左右边距 | **32 px**（可选 16/24/32/40/48） | 沿用现有高密度档内容内缩值 |
| 首行缩进 | **2 全角字符**（可选 0/1/2/3） | 中文书籍标准排版 |
| 对齐 | **两端对齐**（可选左对齐） | 中文正文几乎总是两端对齐，左对齐在中文里显得破碎 |
| 章节名 | **页首**，字号小于正文，可居中或左对齐 | 已确认：顶部是章节信息，不是页脚 |
| 页码 | **右下**，约为正文字号的 70%，低对比（4 级灰） | 已确认 |
| 想法数 | **左下**，与页码同尺寸 | 已确认（纸读 v1 无社交，此项见 §5.9 的替代方案） |

**章节名位置已定论：在顶部，不在页脚。** 顶部显示章节信息，页脚显示页码。**默认状态没有"书名页脚"。**

### 5.5 配色系统与其在墨水屏上的命运

#### 品牌色

微信品牌绿 **`#07C160`**（微信读书沿用为选中/主按钮色）。*注：V4.4.2 时代的产品分析把它描述为**蓝色**，说明主色在历史版本中变过；绿色是当前正确的。*

#### 阅读页配色（实测采样值）

以下十六进制值来自一位用户脚本作者**逐张采样 40 张官方手机版截图**（4 配色 × 5 背景 × 2 轮）的结果，采样方法在源码注释中明确说明：

| 主题 | 背景 | 正文 | 边栏 | 卡片 | 面板 | 次级/图标 |
|---|---|---|---|---|---|---|
| **白色** | `#f8f8fa` | `#0d141e` | `#f8f8fa` | `#ffffff` | `#f4f5f7` | `#858c96` |
| **米黄** | `#f5efd9` | `#3d3427` | `#f5efd9` | `#fbf7ea` | `#f2eedd` | `#8a7d63` |
| **青绿** | `#c0edc6` | `#2f3a2c` | `#c0edc6` | `#dcf6e0` | `#c9ebcc` | `#6d7d68` |
| **夜间** | 官方深色 | — | — | — | — | — |

分隔线为 `rgba(33,40,50,.1)`（白）/ `rgba(90,72,45,.14)`（米黄）/ `rgba(47,58,44,.14)`（青绿）。
**注意**：手机版有 4 个配色主题，**网页版只有白/夜间**——脚本的存在本身就是为了补回手机版的三色。

#### 背景纹理是**独立于配色的第二个维度**

手机版提供 **5 种背景**，与配色**自由组合**：**纯色 / 纸纹 / 素纸 / 云 / 月**。
其中「月」是在右上角（x≈89%、y≈1%）的一个月亮，可见宽度约为阅读区的 21%，**大部分被裁在屏幕上方之外**。
作者的关键观察：*"同一种背景在不同颜色下色调不同——实测：背景④在白色下是蓝天、米黄下是暖灰、青绿下是淡绿"*。而且官方纹理是**照片**（云纹的底是雪山、月纹是带陨石坑的月面），不是矢量。

**[未证实]：** 当前微信读书**没有**叫"羊皮纸"的独立主题。最接近的是「米黄 + 纸纹/素纸」。**如果设计文档里写"羊皮纸主题"，那是我们自己的发明，不是微信读书的主题名。**

#### 灰度可读性分析（对墨水屏的决定性）

按相对亮度 Y 估算对比度：

| 主题 | 背景 Y | 正文 Y | 对比度 | 1-bit 抖动后 | 16 级灰 |
|---|---|---|---|---|---|
| 白色 `#f8f8fa`/`#0d141e` | ~0.94 | ~0.007 | **~19:1** | ✅ 优秀（干净映射为黑白） | ✅ 优秀 |
| 米黄 `#f5efd9`/`#3d3427` | ~0.86 | ~0.036 | **~11:1** | ✅ 良好（阈值后与白色几乎一致） | ✅ 优秀 |
| 青绿 `#c0edc6`/`#2f3a2c` | ~0.78 | ~0.040 | **~9.5:1** | ⚠️ **背景是中灰而非近白 → 整页抖动出网点** | ✅ 良好 |
| 夜间 | 低 | 高 | ~12:1 | ⚠️ 需整屏反色 | ⚠️ |

**四条对纸读有直接约束力的结论：**

1. **白色与米黄可以无损迁移。** 米黄 Y≈0.86 足够亮，用固定阈值二值化后与白色本质相同。
2. **青绿是唯一的问题项。** 背景亮度只有中灰点的约 4 倍 → **1-bit 下整页会出现可见网点**，这恰恰摧毁了"像纸"的质感。**处理：1-bit 下要么把青绿渲染成与米黄同亮度的平坦浅灰，要么直接砍掉它。**
3. **夜间模式在墨水屏上是个陷阱。** 真正的墨水屏"夜间"= 整屏反色，会（a）显著加重残影、（b）某些面板上对比度反而下降、（c）必须整屏全刷。
   ⚠️ **必须整屏重绘，绝不能"换个类名就地重设样式"。** 网页版有据可查的同类 Bug：因为一部分正文被光栅化进 `<canvas>` 位图、**文字颜色在绘制时就烤进去了**，只翻 CSS 类不会触发引擎重绘，于是"它还以为在黑夜、继续按浅色画字"。**纸读把夜间模式实现为一次完整的重新分页渲染 + 全刷，而不是样式层切换。**
4. **不要模仿 `#f8f8fa` 的纯白。** 微读的白是**刻意不纯白并带一点蓝调**的。但在墨水屏上，**纯白就是纸张未通电的本色，是最舒服的状态**。去模仿那点蓝调只能靠抖动，纯属倒退。**墨水屏的"白"= 面板自然白。**

### 5.6 交互模型

#### 点按三区（默认左=上一页，官方可反向）

默认是**三区**模型，且有官方开关可以反转：

| 区域 | 默认行为 |
|---|---|
| **左 ~30%** | 上一页（若开启"点击左侧翻到下一页"则反转） |
| **中 ~40%** | **呼出/收起工具栏**（官方原文："点击屏幕中间"） |
| **右 ~30%** | 下一页 |

**[推断]**：30/40/30 的横向切分比例未公开，是本文的提议；"左=前、中=菜单、右=后"的行为是确证的。
**长按任意位置**启动文本选择（产品分析指出："用户的手势操作不再是左滑的时候"工具栏出现——即滑动是翻页，其他手势是选择/菜单）。

#### 滑动

- **横滑** = 翻页。翻页方式可选：**覆盖 / 平移 / 仿真（卷曲）/ 上下滚动**。
- **上下滚动是一等公民的阅读模式**，不是降级方案。

#### 三种划线样式

官方 API 确证存在多种划线样式（`updated[].colorStyle`、`underlines[].type`），但知乎上专门解释"为何有 3 种划线"的问答页返回 **HTTP 403**，无法取得原文。以下为 **[推断]**：

| 样式 | 含义 | 证据 |
|---|---|---|
| **实线** | 自己划的线 | `colorStyle` 字段存在 |
| **波浪线** | **热门划线**（很多人划） | `/book/bestbookmarks`（Top 20）+ `/book/underlines` 提供 `count`/`score` 热度 |
| **虚线** | **他人/好友**的划线 | 产品分析原文："有人划过线的句子会以**虚线**形式显示出来" |

唯一有确凿出处的行为是"虚线 = 他人的划线"，以及一个**非常值得抄的交互**：

> 如果阅读的人也想标记，**只需随意点击虚线的任何地方就会自动选中虚线部分内容**，无需用户手动从文字开头到结尾再画一遍

#### 选段弹出菜单

从产品拆解列举的阅读页核心功能反推（**[推断]**）：**复制 · 划线 · 写想法 · 查询 · 分享**。

**一个重要事实**：墨水屏版微信读书（V1.9.8，2024-09）**支持划线 + 记录想法，但唯独不能复制文字**——一位作者为此专门装了 flomo 来摘抄，并在文章中反复抱怨；该版本反而上线了「涂鸦笔记」（在页面上手写，像纸书一样）。
— [微信读书墨水屏：如何"正向"产品设计？](https://m.163.com/dy/article/JCJPOLDU0511805E.html)

**这是一次有意识的产品取舍**（作者观点：书读完后留下更多的是笔记，手写的价值高于复制粘贴）。**纸读需要明确决定是否继承它。**

### 5.7 在墨水屏上必须换机制的四个地方

#### ① 进度滑块 → 离散档位 + 即时预览

官方原则是"拖拽进度条而不是定制分级，让读者找到更匹配的度"。**精神要保留，机制必须换**：连续拖拽滑块在墨水屏上意味着**连续局部刷新 + 残影**，观感极差。
**纸读的做法**：改成**离散档位 + 变化即时生效的内联预览**（字号/边距变一次、刷新一次、看到真实效果）。用户照样是"看着效果调"，但每次调整都是**一次干净的刷新**。
**进度跳转**则改用"章节列表 + 页码输入 + 上一章/下一章"，而不是拖动。

#### ② 阴影 → 1px 实线

微读的底部工具栏靠一个 `.showShadow` 的模糊投影与正文分隔（`box-shadow: 0 -.3px 20px rgba(0,0,0,.16)`）。**模糊是连续色调效果，在 1-bit 上是灾难。**
**纸读的做法**：一律换成 **1px 实线分隔**。这是墨水屏的标准解法，也是**从 App UI 移植到墨水屏时最常见的错误。**

#### ③ 浮动圆角按钮 → 扁平 + 1px 描边

`.readerControls_item` 带 `border-radius` + 投影，是 LCD 惯用法。
**纸读的做法**：**1px 黑框的扁平矩形**；常驻操作交给屏外三个电容键。

#### ④ 渐变色 → 平坦填充 + 数字

书架进度徽章、统计图里的渐变**在 1-bit 下会抖成网点**。
**纸读的做法**：**平坦填充 + 1px 边框 + 数字百分比**。

### 5.8 逐元素"墨水屏存活表"

| 元素 | 1-bit | 16 级灰 | 纸读的处理 |
|---|---|---|---|
| 正文 | ✅ 完美 | ✅ | 直接保留。**绝不对 CJK 字形做抗锯齿抖动** |
| 章节名（顶部） | ✅ | ✅ | 保留。层级用字重/1px 细线，小字号不要只靠大小区分 |
| 页码（右下） | ✅ | ✅ | **保留，不改成百分比**。离散、锐利、纸书原生 |
| 想法数（左下） | ✅ | ✅ | 保留为文字形式（纸读 v1 无社交 → 改为**本书书签数/本页笔记数**，见 §5.9） |
| 进度滑块 | ❌ | ⚠️ | **改为离散档位 + 章节列表**；若要进度条，用**实心填充 + 1px 黑描边**，绝不用渐变 |
| 渐变进度条 | ❌ | ⚠️ | **平坦填充 + 1px 边框 + 数字** |
| 阴影（`.showShadow`） | ❌ | ❌ | **换成 1px 实线**。移植时最常见的错误 |
| 浮动圆角按钮 | ❌ | ⚠️ | **扁平矩形 + 1px 黑框**；常驻操作交给电容键 |
| 工具栏浮现动画 | ❌ | ❌ | **瞬时出现/消失**，一次全刷完成 |
| 5 种纸纹背景 | ❌ 保留 1 种 | ⚠️ 云/月勉强 | 纹理是照片，1-bit 下抖成噪声或塌成灰块。**只保留「纯色」** |
| 4 种配色 | ❌ → 1 种 | ✅ → 2 种 | **1-bit：单一主题（面板自然白 + 黑）。16 级：白 + 一个与白色同亮度的米黄** |
| 夜间模式 | ⚠️ 代价高 | ⚠️ | 若要提供，**必须整屏重绘**，绝不就地换样式（§5.5 结论 3） |
| 三种划线（实/波/虚） | ✅ 存活 | ✅ | **线型是 1-bit 上最理想的编码通道**。实线=自己、波浪=热门、虚线=他人；再加**线宽**做冗余线索 |
| 高亮底色 | ⚠️ 慎用 | ✅ | 1-bit 下灰底会抖动并啃掉字形边缘 → **1-bit 优先用下划线，不用底色填充** |
| 封面网格书架 | ❌ | ⚠️ | 封面是官方墨水屏版唯一承认"留彩色"的东西。**1-bit 下书架从封面网格改为文字列表**（书名/作者/进度/状态）。这是比听起来更大的 IA 改动 |
| 读完/面具角标 | ⚠️ → 文字 | ✅ | 封面角落的小彩标会消失 → **状态移到列表行内**（`已读完` / `私密`） |
| 勋章 | ❌ 全删 | ❌ | 插画驱动，无单色形态 |
| 海报生成/分享 | ❌ 全删 | ❌ | 设备外功能 |
| 仿真翻页 | ❌ 全删 | ❌ | 逐帧动画，不可能也无意义 |
| 自动阅读（自动滚动） | ❌ 全删 | ❌ | 依赖平滑连续滚动，墨水屏最坏场景 |
| 听书 / TTS | ❌ 全删 | ❌ | 需音频硬件与播放器 UI；官方墨水屏版也已砍掉 |

### 5.9 该抄的与绝对不该抄的

#### ✅ 该抄的七条（按价值排序）

1. **官方墨水屏版的一屏 IA。** 搜索 / 书架 / 榜单，一件事一屏，**没有 Tab**。官方已经替我们验证过这条路。
2. **"无装饰阅读 + 单一手势唤起一切"。** 整套导航都藏在一次中央点按之后。本机还有物理键，所以**阅读屏可以 100% 是正文**，翻页零屏幕成本。
3. **纸书隐喻而非 App 隐喻。** 具体表现：**用页码不用百分比**、**章节名做书眉**、扉页→正文→读完页的顺序。这是最可迁移的一条，**而且在墨水屏上比在 LCD 上更容易做对**。
4. **精确续读。** 关掉再打开，自动回到上次那本书的最后一页。产品拆解原话把这比作"纸质阅读中的书签"。**这是史上最便宜的留存功能，不可妥协。**
5. **零动画、零干扰。** 墨水屏评测把"没有动画效果，也没有弹窗、广告、推送"称作它最大的优点。**在墨水屏上这不是克制，是物理**——动画等于全屏刷新加残影。**纪律在于"不要加"：不加 spinner、不加 toast、不加进度条动画。**
6. **"不是一个人在读书"的环境化痕迹。** 角落的想法数、"X 人划线"热度标签、他人的虚线划线、**点虚线即采纳该划线范围**。这是微信读书最独特的情感载荷，且**在 1-bit 上完美存活**（一个数字 + 一条虚线，零刷新成本）。**对纯阅读设备而言，这是最划算的一条**——它给出了"不孤单"的感觉，却不带来任何社交机制的负担。
   > ⚠️ 但本机是离线设备、且用户明确要"纯阅读"。**纸读 v1 不发想法、不联社交**；把这份"痕迹感"改写为**本地化版本**：页脚左下显示**本页/本书的书签数**、**本书已读时长的极简显示**。等接入微信读书后，再把真实热度数据接进来（§6.3 的 weread 模块）。
7. **滑动条的精神 → 离散档位。** 见 §5.7①。

#### ❌ 绝对不该抄的（在 1-bit 上是负资产）

| 不抄 | 原因 |
|---|---|
| 4 个底部 Tab + 信息流首页 | 需要滚动与快速刷新；官方墨水屏版已砍 |
| 书城 / 推荐卡片流 | 依赖封面彩图；官方墨水屏版唯一保留彩色的地方就是封面，说明这是它的软肋 |
| 朋友的想法 / 小圈子信息流 | 无限滚动社交流，与墨水屏刷新模型根本冲突 |
| 每日一答 / 翻一翻 / 组队抽卡 / 无限会员日 | 游戏化营销，与"纯阅读"直接对立 |
| 勋章 / 读书排行 / 海报生成 | 海报生成不可能；勋章是插画驱动。**用纯文字的"连续 N 天 / 本周 4 小时 12 分"替代** |
| 分享到微信/朋友圈 | 无微信集成；且分享图是黑底金字海报 |
| 自动阅读 | 依赖平滑滚动 |
| 仿真翻页 | 逐帧动画 |
| 涂鸦笔记 | 需手写笔 + 数字化层，本机无 |
| **复制文字** | ⚠️ **反例**：官方墨水屏版**砍掉了复制**，但从"笔记可导出"的角度看，**这是它最值得反悔的一个决定**。纸读 v1 也没做文本选区（§5.6 决策 3），但**应在 v2 用"段落级选中"补上** |

#### 💡 一条本设计要主动改进的地方

**把"想法数"这个位置换成本地化的阅读元信息。** 官方左下的"12 个想法"依赖联网社交。纸读在同一位置放**本书的进度信息**（如 `本书 37%` 或 `第 12 章 / 共 42 章`），既保持了页脚的视觉平衡与"纸书书眉/页脚"的惯例，又完全离线可用。当用户接入微信读书后，这个槽位可以无缝换成真实的想法数。

## 6. 纸读 PaperRead 固件设计 v1

### 6.1 设计目标与非目标

**目标（v1 必须达成）**
1. **开箱即用的中文阅读**：不装 SD 字库，内置字库就能完整读中文小说（含常用生僻字），无 `□`、无"下载字库"弹窗。
2. **中文文件名/标题零乱码**（修 B1）。
3. **翻页手感优先**：纯文本翻页走 DU 快刷，残影自适应清理。
4. **微信读书风格的双层 UI**：首页 ⇄ 阅读页，其余全是浮层。
5. **阅读时长统计**——但按决策 8，只有**累计时长 / 会话次数 / 读完本数**三个纯累加指标（无今日、无连续天数、无每日目标）。用户已有的约 6.3 小时累计会被迁移保留（§7.5.3）。
6. **可无缝继承现有 SD 卡**：读得懂 `.crosspoint/` 的设置、进度、统计，不丢数据。
7. **省电**：睡眠电流与唤醒路径跟 CrossMux 一致（PMU 深睡 + 拾取唤醒可选）。

**非目标（v1 明确不做）**
- ❌ 不做书城/发现/社交/排行榜（设备无网络场景）。
- ❌ 不做游戏（五子棋/数独/象棋/扫雷/2048/木鱼）、丑头像、老黄历。
- ❌ 不做 AirPage 相册（MQTT 常连、Flash 与内存开销大）。
- ❌ 不做 PDF/MOBI/CBZ（解析成本远超收益）。
- ❌ 不做文本选区划线（见 §5.6 决策 3）。
- ❌ 不做 BLE 翻页器（v1；架构上留口）。
- ❌ 不做字体在线目录下载（改为**内置足够好**，SD 字体仍支持本地加载）。

### 6.2 选型决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 基线 | **fork `0x1abin/crossmux`（MIT）** | 唯一已有可用 `readpico` BSP + 桌面模拟器 |
| 分支策略 | 建立 `paperread` 分支，**保持与 upstream 可 rebase** | 长期靠 upstream 修 BSP/驱动 bug，只在 `src/activities/` 与 UI 层做减法 |
| 语言/构建 | C / PlatformIO（沿用） | 零迁移成本 |
| **显示路径** | **沿用 `EpdiyLcd` + freeink-sdk**（`FREEINK_EPDIY_LCD_CONFIG=readPicoEpdiyConfig`） | 已合主干并已在真机点亮；**注意不是 M5GFX/LovyanGFX i80——那条路径已被上游删除**（见 §1.2） |
| 灰度 | 正文 = 2-bit AA 文本；图片/锁屏 = 16 级 | 沿用 `READ_PICO.grayscaleLevels = 16` |
| **字体封装** | **沿用 `.cpfont` v4（2-bit AA + 区间索引）**，**不换** M5Stack 生态的 TTF→BIN 格式 | 见附录 D：该格式是 **1-bit 无抗锯齿**且**逐字 20 B 索引**，两项都不适合本机 |
| **字体原则** | **阅读字体一律预栅格化，运行期绝不解析 TTF**；缺字在**构建期**用 fallback 字体补齐 | 借鉴 TTF→BIN 实践的正确部分；见附录 D.4 |
| **正文字号** | **默认 20pt**，可选 12 / 14 / 16 / 18 / 20 / 22 / 24pt | 用户指定；版式见 §1.4 |
| 配置目录 | **新建 `.paperread/`，首次启动从 `.crosspoint/` 迁移** | 见 §8.1 |
| 应用框架 | 沿用 FreeInkUI `Activity` 体系，但**只保留约 8 个 Activity** | 见 §6.3 |
| **网络代码** | ✅ **全删**（WiFi / SNTP / HTTP / WebDAV / mDNS / wolfSSL / SecureNet） | 决策 6；WiFi 原本只有传书一个用途 |
| **传书方式** | **人为拷贝到 SD 卡 `books/`** | 决策 6；低频操作不值得常驻网络栈 |
| **USB 挂载** | ❌ **不做**（因此无需放弃 `firmware_tuned` 的 32–37 KB 堆回收） | 决策 6；读书时把卡拔出来插电脑即可 |
| **OTA** | ⚠️ 改为**从 SD 卡本地更新**（A/B 双槽 + 校验 + 回滚） | 删网络后必须补上，见 §6.9.3 |
| **UI 入口** | **仅三个**：最近阅读 / 书库 / 设置 | 决策 7；统计并入首页，见 §7.2 |
| **时间与日期** | ✅ **全删**（RTC 日期读取 / 校时 / 页脚时钟 / `dayOrdinal` / 按天统计）；**但 PMU 驱动保留**（电量与电源键要用） | 决策 8；统计改为纯累加器，见 §7.5 |
| **划线/批注** | **段落级**（不按字符），**只用线型不用底色** | 决策 4；1-bit 上底色会抖动并啃字形，见 §6.8 |
| **拾取唤醒** | SC7A20H 直写寄存器 + GPIO1 作深睡唤醒源，**默认关闭** | 决策 5；有误唤醒风险，需可校准，见 §6.8 |
| 省空间的编译开关 | 去掉非阅读能力后启用 `CONFIG_COMPILER_OPTIMIZATION_PERF` | 换 `-O2` 提渲染速度 |
| i18n | **33 语言 → 仅 zh-CN + en** | 单笔最大的 Flash 节省之一，零体验损失 |

### ✅ 结论修订二（2026-10-06 实测）：**三档字库完全可行 —— 撤销"砍 14pt"的决定**

上一版修订基于**同步卡 `.cpfont`** 路径实测（三档 5.4 MB），据此砍掉了 14pt。**那是用错了路径**——固件内嵌走的是 `fontconvert.py` → **C 头文件**，两条路径的体积特性完全不同：

| 关键差异 | `.cpfont`（SD 卡路径） | **内置 C 头文件（固件路径）** |
|---|---|---|
| 字形选择 | 区间内**每个码位**都要字形 | 支持 **`--characters`**：**只导出指定字符** |
| 压缩 | ❌ 无 | ✅ **支持 DEFLATE（`--compress`）** |
| 设备端支持 | — | ✅ **已在生产验证**：上游 `notosans_12/14/16/18_*` 全部 `compressed: true` 并带 `EpdFontGroup` 表 |
| GB2312 @ 20pt | 2,879,274 B | **1,153,378 B** |
| GB2312 三档 | 5,666,892 B（❌ 放不下） | **2,679,813 B（2.56 MB）** ✅ |

**压缩收益约 2.4–2.5×**：DEFLATE 对 CJK 2-bit 位图极有效（大片空白 + 规律笔画）。

| 20pt | 1,006,222 B | 103,236 B | 43,092 B | 828 B | **1,153,378 B** | 2,861,313 B |
| **三档合计** | | | | | **2,679,813 B（2.56 MB）** | 5,613,009 B（5.35 MB） |

> 尺寸依据（实测源码）：`EpdGlyph` = **14 B**（`width` u8 + `height` u8 + `advanceX` u16 + `left` i16 + `top` i16 + `dataLength` u16 + `dataOffset` u32），`EpdUnicodeInterval` = **12 B**，`EpdFontGroup` = **18 B**。glyph 数 7,374（含 1 个替换字形）——**glyph 表在每个字号都要一份，是固定 103 KB/档**。

#### 修正后的预算

```
可用于固件                                         6,029,312 B
字库三档（内置，压缩）                             -2,679,813 B
────────────────────────────────────────────────────────────
剩余                                               3,349,499 B  ✅ 充足
```

**结论**
- ✅ **20pt + 14pt + 12pt 三档全部内嵌**。**撤销**上一版"14pt 由 20pt 缩放替代"的降级决定。
- ✅ 字库占 2.56 MB，**余约 3.35 MB** 给固件本体——比原先以为的更宽松。
- ✅ **必须开 `--compress`**。不开则三档 5.35 MB，会把预算吃光。
- 18 / 22 / 24pt 仍走 SD 字库（用户已装）。

**仍未解决的一处覆盖缺口**：GB2312 的 7,594 个码位里，**Noto Sans SC 只有 7,373 个有字形**（差 221 个）。这些字在设备上会缺字。对策见附录 D-2（构建期扫描实际藏书、定向补字）。

**体积兜底降级链（已按实测重排）**

```
① 先降 12pt（页脚/副标题用 14pt 或 20pt 缩放）  → 省 724,941 B
② 再降 14pt（列表项/设置标题走 SD 字库）        → 再省 801,494 B
③ 20pt 缩到 3500 常用字（不缩字号，缩覆盖）      → 省约一半
④ 最后手段：关掉 --compress（❌ 会爆预算，不可作为退路）
```
> **顺序理由**：20pt 是正文（用户指定），**绝不缩字号**；先砍小字号档位，最后才缩 20pt 的字符覆盖面。这与"16pt 方案"的降级顺序正好相反。

**纸读 v1 的目标档位（最终）**
- 内嵌 **20pt（正文默认，主档位）+ 14pt + 12pt**，覆盖 **GB2312 一二级（7,373 个有字形的码位）**，全部启用 DEFLATE 压缩。
- 18 / 22 / 24pt 大字号依赖 SD 字库。



> ~~本表最重要的一句话：`每 1000 字 ≈ 380 KB` 这个经验值来自 `chinese-build.md`…~~
> **本段已被实测推翻，保留作教训记录**：先前按"每 1000 字 ≈ 380 KB"与"墨迹框 96 B/字"两个口径推算，都得出约 700 KB 量级；**实测是 2,812 KB（20pt）**。原因是**字形按 em-box 存储**（含 bearing 与行距），不是按墨迹裁剪。详见 §6.4.1。


> 为什么是 GB2312 二级而不是"3500 常用字"？实测用户书架里有《哈利波特全集》《那不勒斯四部曲》《枪炮、病菌与钢铁》这类**人名地名密集**的书，以及网文（《练阴阳，合欢喜，成大道》）。这类书正是"生僻字/异体字"高发区。3500 字不够，**GB2312 的 6,763 字才是中文小说的实际下限**。这是"纯阅读"换来的最大价值。

                    ┌────────────┐  ┌──────────────┐
                    │ ReaderActivity│ │LibraryActivity│
                    │  （正文）     │ │ 列表/网格     │
                    └──────┬───────┘ └──────┬───────┘

**关键约束**
- 浮层**互斥**，不允许叠加（墨水屏叠加会重绘整屏且产生残影）。
- 每个浮层打开时**必须先快照当前正文位图**，关闭时**恢复快照**而不是重排正文。CrossMux 已有这个模式（"Closing the EPUB toolbar restores the firmware's B/W page snapshot"），沿用。
- 首页**不设顶部状态栏**（省 48px），电量只在首页底部右下角一行小字。

### 6.6 阅读页刷新策略（决定"手感"）

| 场景 | 刷新模式 | 原因 |
|---|---|---|
| 纯文本翻页（前/后） | **DU 快刷**（差分） | 最快，~150–250 ms |
| 每 N 页（默认 N=6，可配 1–20） | **GC16 全刷** | 清残影 |
| 翻页方向反转（前→后 或 后→前） | **立即 GC16 全刷** | 反向残影最明显，是"脏屏"的主因 |
| 呼出/收起工具栏 | **Grayscale 抖动浮层**，仅重绘浮层区域 | 不重排正文，避免整屏闪烁 |
| 打开新书 / 换字体 / 改字号 | **GC16 全刷** | 必须干净重绘 |
| 章节首屏 | **GL16 灰度** | 灰度更细腻；CrossMux 记录 GL16 = 常规灰度 |
| 首屏插图页 | **16 级原生灰度** | ReadPico 独有能力 |
| ✅ 用户偏好对齐 | 沿用 `refreshFrequency`（当前=2）与 `statusBarProgressBar`（当前=2）语义 | 迁移不丢设置 |

**新增的自适应逻辑（v1 亮点）**：
```
维护一个"脏度"计数器：
  正向连续翻页      → dirty += 1
  反向翻页          → dirty += 4   （反向最脏）
  浮层开合          → dirty += 2
  图片/灰度页       → dirty = 0    （灰度页自带全刷）
  dirty >= N(默认6) → 触发 GC16 并清零
```
这比 CrossMux 的固定 `refreshFrequency` 更聪明，且不需要新配置项（沿用 N 的默认值）。

### 6.7 内存策略（内部 RAM 只有 30–45 KB 可用）

| 资源 | 位置 | 说明 |
|---|---|---|
| 前端帧缓冲（1bpp） | PSRAM | 684×1216/8 ≈ **104 KB** |
| 4bpp 灰度暂存 | PSRAM（复用 AirPage 释放的那个 415,872 B 缓冲） | 删掉 AirPage 后**这块可以直接让给阅读路径** |
| 后端帧缓冲 | PSRAM | 同上 |
| 字库字形位图 | PSRAM（动态、LRU） | 每档只保活一个 family |
| 字库索引表 | PSRAM | 6,763 字的区间表约 12 B/区间，可控 |
| 分页缓存 | **SD 卡**（`sections/*.bin`） | 沿用 CrossMux，不占 RAM |
| 大 JSON 解析器 | **流式解析**，不整块载入 | **修 B2**：用 16 KB 流式缓冲 + SAX 风格状态机替代需 64 KB 连续内存的解析器 |
| EPUB 解压 | 逐条目流式 | 不整本解压 |

**修 B2 的具体方案**：把 EPUB CSS 解析器改为**两遍流式**——
- 第一遍：只扫描选择器名，把命中的选择器哈希写入 PSRAM 里的一张紧凑表（每条 16 B）。
- 第二遍：只对命中的规则解析声明块。
这样内存需求从 64 KB 连续降到 **≤16 KB**，且 CSS 不再是"有内存就生效、没内存就静默丢弃"。

### 6.8 段落级划线 / 批注（决策 4）与拾取唤醒（决策 5）

#### 6.8.1 为什么用「下划线」而不是「高亮底色」

微信读书的三种划线都是**线型**编码（实线=自己、波浪=热门、虚线=他人，见 §5.6）。而在 1-bit 屏上加**底色高亮**有两个问题：灰底必须抖动 → 整行出现网点 → 并且**啃掉字形边缘**（CJK 笔画密集，代价远大于拉丁文）。
**结论：纸读 v1 只用线型，不做底色填充。** 这既是 §5.8 存活表的结论，也顺带解决了"如何区分划线类型"——**线型是墨水屏上比颜色更丰富的信息通道**。

| 线型 | 语义 | v1 |
|---|---|---|
| **实线**（1 px，字底下方 2 px） | **自己的划线** | ✅ |
| 虚线 | 他人 / 共享划线 | ⬜ v2（离线设备无同步源，暂无意义） |
| 波浪线 | 热门划线 | ⬜ v2 |

冗余线索：**自己划线 = 1 px 实线；所在段有批注 = 段左边缘 3 px 竖条 + 段末小三角**。这样"有划线"与"有批注"一眼可分。

#### 6.8.2 交互：按**段落**选，不按字符选

§5.6 决策 3 已定：**不做字符级拖动选区**（墨水屏 200–400 ms 刷新下拖动选取极难用，且需高频局部重绘）。改为：

```
阅读页 · 长按中键（或长按正文任意处）
        ↓
进入「段落选择模式」：当前段落整段加框（4 级灰抖动填充，不是实心黑）
        ↓
中键 = 上移一段   ·   右键 = 下移一段   ·   左键 = 取消
        ↓
再长按中键 = 确认选区
        ↓
浮出小菜单：  [ 划线 ]   [ 划线并写批注 ]   [ 取消 ]
```

- **按段落选**而非按字符：段落是 EPUB 排版里天然存在的边界，**恰好对应纸上"划一句话"的粒度**。
- **不引入新手势**：长按 = 选区（§5.6 已定）。阅读页中键长按原本是"快速书签"，现改为**"长按进入选区"**；书签改由工具栏「标记」面板处理（§7.3）。
- **与翻页手势不冲突**：中键**短按**仍是"呼出/收起工具栏"，只有**长按**才进选区。

#### 6.8.3 批注：只做"一句感想"，不做富文本

| 项 | 决定 | 理由 |
|---|---|---|
| 输入方式 | **内置拼音 / 首字母候选输入** | `read-pico-reader` 已有可借鉴实现（`read_pico_search` + pypinyin 字典，MIT） |
| 长度上限 | **280 字** | 够写一段感想；再多就该另开文件 |
| 富文本 | ❌ 纯文本 | 墨水屏排版与存储都不划算 |
| 展示 | 段左 3 px 竖条 + 段末小三角；点它 → 浮层显示批注全文 | 不侵入正文 |
| **导出** | ✅ **v1 支持「导出本书笔记到 SD 卡」为 `.txt`** | **这是删掉微信读书后最重要的补偿**：笔记必须拿得出来 |

#### 6.8.4 存储模型（关键：抗重排）

⚠️ **绝对不能用字符偏移做锚点。** 用户一改字号/边距，分页与字符位置全部变化，划线就会错位到别的句子上。

```json
// .paperread/annotations/<bookId>.json
[{
  "id": "a1",
  "spineIdx": 12,              // ① 主锚点：章节序号
  "paraIdx": 47,               //    章节内第 N 个块（EPUB 的 <p>/<div> 边界）
  "paraSnippetHash": "9f3a...",// ② 校验：该段前 32 字的 FNV-1a 哈希
  "charStart": 0,              // ③ 段内偏移（只有在这一级才用到字符位）
  "charEnd": 41,
  "excerpt": "...",            // 冗余保存原文，便于导出与容错
  "note": "...",
  "style": "solid",
  "createdAt": 1791027239
}]
```

**为什么这样设计**：`spineIdx + paraIdx` 在**换字号 / 换边距 / 换字体时完全不变**（只依赖 EPUB 结构，不依赖排版结果）。`paraSnippetHash` 在书的版本变化（重新拷贝、被替换）时用于**校验并纠正**——哈希不符就回退到用 `excerpt` 全文搜索定位，再不行才降级标为"失联"。
> 这与 CrossMux 的 section 缓存失效策略是同一思路：**把"结构锚点"与"排版结果"分开**——排版结果可随时丢弃重建，结构锚点必须持久。

**渲染接入点**：分页缓存（`sections/N.bin`）需为每个 `TextBlock` 附带一个 `annotationMask`（该段是否有划线/批注），绘制时按 mask 画线。
⚠️ **改动划线后必须让当前 section 的缓存失效重建**——沿用 CrossMux 现有的"render spec 变化即失效"机制，把 `annotationMask` 计入 section 缓存 key。

#### 6.8.5 拾取唤醒（决策 5）

**硬件现状**：SC7A20H @ I²C `0x19`（`WHO_AM_I = 0x11`），**只有加速度计、无陀螺仪**（`gx=gy=gz=0`），中断脚 **INT1 = GPIO1**。上游记录该能力 *"not covered by the current `Imu` API"*，即 `Imu` 抽象层没有暴露中断寄存器，**必须绕过它直写寄存器**。

| # | 工作 | 细节 |
|---|---|---|
| 1 | 配 `CTRL3` 使能 INT1 | 把 AOI1（加速度中断）路由到 INT1 |
| 2 | 配 `AOI1` / `HPIS1` 阈值与时长 | "拿起"判据参考值：**约 350 mg 阈值 + 600 ms 内两次上升沿触发 + 800 ms 冷却**（这是 `read-pico-reader` 在"晃动翻页"里验证过的参数，可直接借用） |
| 3 | GPIO1 配成**深睡唤醒源** | ESP32-S3 上 GPIO1 属 **RTC IO**，可用 `esp_sleep_enable_ext1_wakeup()`；与 PMU 电源键并列为两个唤醒源 |
| 4 | 共享 I²C 总线 | **必须走现有递归 I²C 锁**。上游 `read-pico.md` 明确记录这条纪律（"PMU commands hold the existing recursive I²C lock"）；SC7A20H 挂在同一 SDA39/SCL40 上，不能绕锁 |

**主要风险是误唤醒。**
- 阈值太松 → 放包里走路就唤醒，**续航肉眼可见变差**。
- 阈值太紧 → 拿起来不亮，用户以为坏了。

**应对**：① 做成**可校准开关**（设置里给"灵敏度：低/中/高"+ 一个"测试当前灵敏度"的实时读数页）；② **v1 默认关闭**，由用户主动开启；③ 开启后把**唤醒次数计入阅读统计**，让用户能自查是否异常。
**功耗验证（必须做）**：开启后**静置 24 小时记录耗电**，与关闭时对比；差异超过 10% 则默认值改为"关闭"。

### 6.9 完全离线 + 本地 OTA（决策 6）

> 决策 6 是"USB 挂载不做、WiFi 也不做，传书仅靠人为考入"。这不只是"少两个功能"——它让纸读**成为一台不含任何联网代码的设备**，并腾出约 400 KB 预算。

#### 6.9.1 要物理删除的东西（不是关开关，是删代码）

| 类别 | 具体项 |
|---|---|
| **网络栈** | `WiFi.h` / `esp_sntp` / HTTP 服务器（端口 80）/ WebSocket 上传（81）/ WebDAV / mDNS / DHCP |
| **加密库** | **wolfSSL 5.7.2**，以及 `-DFREEINK_NET_WOLFSSL=1`、`-DFREEINK_CONTENT_WOLFSSL=1`、`-DWOLFSSL_TLS13`、`-DNO_WOLFSSL_ESP32_CRYPT_RSA_PRI` 等一长串 flags |
| **构建步骤** | `pre:scripts/patch_wolfssl.py` |
| **SDK 库** | `SecureNet`、联网用 `JsonSax` / `CatalogList`；OPDS 浏览器；Calibre 无线连接 |
| **凭据存储** | `WifiCredentialStore` → 现有 `wifi.json`（2 个 SSID + 混淆密码）**不再读取**，SD 上原样保留不删 |
| **`main.cpp` 分支** | `WiFi.getMode()` 判断、`JoinNetwork`、`silentRestartToJoinNetwork()`、sleep-event WiFi 入网、`trustedtime::startSync()`、联网字体下载提示 |
| **USB** | USB MSC 路径（ReadPico 本就未启用）、TinyUSB 组件图 |

> **`main.cpp` 是最大受益者之一。** 上游 60 KB 的 `main.cpp` 里大量逻辑在处理"WiFi 会话 / 静默重启 / 联网同步 / 字体下载"的复杂状态机。删掉后主循环变成**纯粹的本地状态机**，可读性与可维护性都会明显改善。

#### 6.9.2 时间与日期：**整条删除**（决策 8 之后本节作废）

> 本节原先要处理"删 SNTP 后靠什么校时"。**决策 8 把时间和日期彻底删除了，所以这个问题不存在了。**

**不再需要处理的事**：PMU RTC 的日期读取路径、`trustedtime` 时钟下限、`clockAutoSync`、手动校时 UI、首次开机的"确认日期与时间"屏、页脚时钟。

**唯一需要小心的地方**：`Rtc` 库与 PMU 协议里"读 Unix 秒 / 设闹钟"的调用点要**全部摘掉**，但 **PMU 本身必须保留**——它同时提供**电量 mV / 千分比 / 充电状态**与**电源键上报**，这两项是必需的。
> 也就是说：**删的是"时间的语义"，不是 PMU 驱动。** 不要因为删时间而把 PMU 初始化一起删掉。

**顺便丢弃的相关设置键**：`clockUtcOffsetQ`、`clockFormat`、`clockAutoSync`、`clockTimezone`、`clockDst`、`clockShowHeader`、`clockHasBeenSynced`（用户现有 `settings.json` 里这 **7 个键**全部丢弃）。

**阅读统计为何不受影响**：新统计只用 `accumulatedMs` / `sessionCount` / `booksFinished` 三个**纯累加器**——不需要知道"今天是哪一天"。详见 §7.5.2。

#### 6.9.3 OTA 改为从 SD 卡本地更新（**必须补上**）

删掉网络后，**固件更新是唯一必须保留的运维能力**——否则以后每次改固件都得拆机。

```
把 firmware.bin 拷到 SD 卡根目录（或 /update/）
  → 设置 → 固件更新 → 「从 SD 卡更新」
  → 校验：项目名 / 型号 / 版本号 / 镜像大小 / SHA-256
  → 写入**非活动的那个 A/B 槽**
  → 写完置 otadata 指向新槽
  → 重启；新固件首启自检失败则由 bootloader **自动回滚**到旧槽
```

这套机制 **CrossMux 与 `read-pico-reader` 都已实现并验证过**，直接沿用：
- CrossMux 已有 "OTA updates (online **or `firmware.bin` on SD**)" —— **只保留 SD 分支，删掉联网分支**即可。
- `read-pico-reader` 可作交叉参考：`Pico-update.bin` 放卡根 → Files → Update，**校验项目名/版本/大小/镜像头，只写空闲槽，完整校验后才切槽，首启失败 bootloader 回退**。

⚠️ **与非活动槽的字体加速缓存冲突**：CrossMux 会用**非活动 OTA 槽**缓存选中的 SD 字体（`CPSDFC1` 头，§A.3）。OTA 与字体缓存**争用同一个槽**。上游的处理顺序是"OTA 自然覆盖它，确认新固件后才回收"。纸读沿用该顺序，但要在**本地 OTA 前显式失效字体缓存**，避免写入被缓存头挡住。

#### 6.9.4 传书流程（人为拷贝）与三个必须处理的问题

**流程**
```
1. 设置 → 电源 → 关闭（避免写入中拔卡）
2. 取出 TF 卡，插到电脑
3. 把 .epub / .txt 拷到 SD 卡根目录的 books/
4. 插回设备，开机
5. 首次进入书库时自动扫描建索引（复用 LibraryBuilder）
```

**问题一：不安全的移除。** 设备没有"安全弹出"，用户可能在写入中拔卡。
→ 应对：**关键写入全部原子化**（`.tmp` + rename，§1.5 已有纪律）+ **挂载检测**：若 SD 挂载失败或根目录不可读，显示明确提示而不是静默空白书库。

**问题二：B1（中文文件名乱码）在这条路径上被放大 —— 升级为阻塞级。**
既然传书完全依赖用户自己命名的文件，**文件名编码就成了唯一的入口标识**。B1 不修，书库里全是乱码书名，而这是用户唯一能看到书名的途径。**B1 从 P0 升级为"传书流程能否可用"的前提条件。**

**问题三：书元数据从哪来。** 人为拷贝没有 OPDS/Calibre 注入元数据。
→ 应对：书库优先读 **EPUB 内嵌 OPF**；TXT 用文件名（**更依赖 B1**）；两者都缺时允许在设备上编辑书名（`read-pico-reader` 有此实现，可借鉴）。

#### 6.9.5 与 `read-pico-reader` 的差异（避免误解为能力缺失）

`read-pico-reader` **有** USB 读卡（TinyUSB MSC）**和** WiFi/热点传书。纸读**两者都不做**——这是明确取舍，不是缺失：

| | read-pico-reader | 纸读 |
|---|---|---|
| USB 挂载 | ✅ TinyUSB MSC | ❌ 不做（读书时把卡拔出来插电脑即可） |
| WiFi / 热点传书 | ✅ HTTP 上传 | ❌ 不做 |
| 代价 | 需放弃堆优化 + 带完整网络栈 | **零代价，且省约 400 KB + 32–37 KB 堆** |

> **判断依据**：离线阅读器的传书频次很低（一本书读几天到几周，一个月传几次）。为每月几次的操作常驻一整套网络栈 + 一个 USB 设备栈**不划算**。把卡拔出来插电脑，30 秒的事。

| 「最近 7 天」柱状图 | 按天统计 → 已删 |
| 「当前连续 4 天 / 最长连续」 | 连续天数本质是日期差 → 已删 |
| 「最近 30 天」热力图 | 按天统计 → 已删 |
| 「日均时长」 | 依赖自然日 → 已删 |
| 官方时长分档 `[60,1800,3600,10800,18000]` | 分档是给热力图用的 → 随热力图一起删 |
| 整个 `StatsActivity` 页面 + 它的 Tab 入口 | 统计只剩一个数字，不值得占一页 |

**同时删掉的技术实现**：`dayOrdinal` 的计算与持久化、跨日切分会话的逻辑、连续天数/最长连续算法、热力图渲染、以及**PMU RTC 的日期读取路径**（§6.9.2 整节作废）。

#### 7.5.2 剩下的内容（3 项，直接显示在首页底部）

```
   累计阅读  6 小时 18 分                                   ← 首页底部一行
   读过 17 本 · 读完 2 本 · 平均每次 14 分钟                  ← 次级，12pt 4级灰
```

| 指标 | 计算方式 | 是否需要时间/日期 |
|---|---|---|
| **累计阅读时长** | `accumulatedMs` 累加 | ❌ 不需要（纯时长） |
| **读过 / 读完本数** | 书库状态计数 | ❌ 不需要 |
| **平均每次** | `accumulatedMs / sessionCount` | ❌ 不需要（纯时长除法） |
| ~~今日 / 连续天数 / 热力图~~ | — | **已删** |

**关键洞察：阅读统计其实从来不需要"绝对时间"。** 只需要两个累加器——**总毫秒数**和**会话次数**——就能给出这三个指标。原来的设计之所以要 RTC 和 `dayOrdinal`，只是为了"按天分组"这个 UI 形式；**把 UI 形式去掉，时间依赖就整条消失了**。

#### 7.5.3 数据格式（改为极简，且不兼容旧 v6）

见 §8.2。新格式只有三个字段：`accumulatedMs` / `sessionCount` / `booksFinished`。

**迁移**：从旧 `reading_stats.json` v6 的 `readingDays[].readingMs` **求和**得到 `accumulatedMs`（把用户已有的 4 天、约 6.3 小时原样带过来），`sessionLog` 的条数作为 `sessionCount`。**旧的按天数据被主动丢弃**——因为决策 8 之后它们没有消费方了。

> 这是本项目里**唯一一处主动丢弃用户数据**的地方，所以特别说明：丢掉的只是"哪一天读了多少"这一维度，**总时长与总次数都保留了**。

## 8. 数据模型与文件格式

### 8.1 目录迁移策略：`.crosspoint/` → `.paperread/`

**决策：新建 `.paperread/`，首次启动执行一次性迁移，`.crosspoint/` 原样保留不清除。**

理由：① 用户可能想切回 CrossMux（保留原目录才能回退）；② CrossMux 文档明确警告"不要为了清缓存就删 `.crosspoint`，那里也有设置和进度"；③ 迁移失败时用户数据仍安全。

```
SD 卡根
├─ .paperread/               ← 纸读的新家
│   ├─ settings.json         ← 迁移自 .crosspoint/settings.json（裁剪 + 新增键）
│   ├─ state.json
│   ├─ recent.json
│   ├─ reading_stats.json    ← **转换为新极简格式**（决策 8 后旧 v6 的按天数据无消费方，见 §8.2）
│   ├─ bookmarks/<bookId>.json   ← 新：书签（CrossMux 的书签存在别处）
│   ├─ epub_<hash>/          ← **直接复用** .crosspoint/epub_<hash>/（不复制，软链接式引用）
│   ├─ library.idx
│   ├─ migration.json        ← 迁移记录（源版本/时间/结果）
│   └─ （无 weread/ —— 决策 3 已删该模块，**不迁移任何微信读书数据**）
├─ .crosspoint/              ← 保留不动，作为回退锚点
├─ fonts/                    ← 不变（用户已装 4 套共 30 个 .cpfont）
├─ books/                    ← 不变
└─ pictures/                 ← 不变
```

**迁移算法**
```
if 存在 .paperread/settings.json:
     正常启动，不迁移
elif 存在 .crosspoint/settings.json:
     1. 校验 .crosspoint/settings.json 可解析（JSON 合法性 + 版本字段）
     2. 逐键白名单映射：新键表 ← 旧键表（未识别的键丢弃，记录到 migration.json）
        ├ 丢弃全部 weread* / contentProfile / langSku / inx* 键（决策 2、3）
        └ 强制 defaultFontSize = 20（决策 1）
     3. 复制 recent.json / state.json
        ├ **不复制 .crosspoint/weread/**（决策 3）
        └ reading_stats.json **做转换而非复制**：把旧 v6 的
          readingDays[].readingMs 求和 → 新格式的 accumulatedMs；
          sessionLog 条数 → sessionCount（§7.5.3）
     4. 记录 epub_<hash> 目录清单到 .paperread/cache_index.json（只记路径，不复制数据）
     5. 写 .paperread/migration.json {fromVersion, at, mapped:N, dropped:[...], ok:true}
     6. 显示一次性提示：「已继承 CrossMux 的阅读进度与统计」
else:
     全新初始化 + 引导页（简化为 3 屏：语言 → 传书说明 → 选字体 → 完成）
     ⚠️ 无"确认日期与时间"屏（决策 8 后设备无时间概念）
```

> **迁移后的一个提示**：用户的 `.crosspoint/weread/` 与微信读书书架数据**保留在 SD 卡上不动**（只是纸读不再读它）。如果将来想切回 CrossMux，微读登录态仍在。


### 8.2 文件格式规范

| 文件 | 格式 | 说明 |
|---|---|---|
| `settings.json` | JSON，**key-value 平铺**（沿用现有风格） | 约 **29 键**，人类可读可改 |
| `reading_stats.json` | JSON，**新极简格式**（**不复用 v6**） | 只有三个字段：`accumulatedMs` / `sessionCount` / `booksFinished`。**无日期、无按天数组、无连续天数**（决策 8） |
| `recent.json` | JSON，`{books:[{path,title,author,coverBmpPath}]}` | ⚠️ **必须 UTF-8 正确编码**（修 B1） |
| `library.idx` | 二进制，magic `CLX1` | 沿用；索引条目增加 UTF-8 长度前缀 |

**`reading_stats.json` 新格式示例**
```json
{
  "accumulatedMs": 22680000,   // 累计阅读毫秒（迁移时由旧 v6 的 readingDays 求和而来）
  "sessionCount": 24,          // 会话次数（旧 sessionLog 条数）
  "booksFinished": 2           // 读完本数
}
```
> **迁移换算**：用户现有 4 个阅读日的 `readingMs` 合计约 **22,680,000 ms ≈ 6 小时 18 分**，会话约 24 次。这两个数字会原样带到新格式。**丢掉的只有"哪一天读了多少"这一维度**（决策 8 后已无消费方）。

### 8.3 书名/作者编码：修 B1 的根因分析

**现象**：`寻迹.epub` 在 `recent.json` 里是 `"瀵昏抗"`。

**根因**：`寻迹` 的 UTF-8 字节是 `E5 AF BB E8 BF B9`。而 `瀵` 的 UTF-8 是 `E7 80 B5`、`昏` 是 `E6 98 8F`、`抗` 是 `E6 8A 97`。观察 `"瀵昏抗"` = `E7 80 B5 E6 98 8F E6 8A 97`——**6 字节**，而 `寻迹` 是 **6 字节**（`E5 AF BB E8 BF B9`）。字节数相同但内容不同 → 说明不是简单的 UTF-8/GBK 误读（GBK 转换会改变字节数），而是**这 6 个字节在某个环节被重新编码了**。

更可能的解释：**FAT/exFAT 长文件名的 UTF-16LE ↔ UTF-8 转换路径出错**，或 **JSON 序列化时对文件名做了二次编码**。`state.json` 里的 `"/瀵昏抗.epub"` 同样错，说明错误发生在**写盘前**，即内存中的字符串已经是错的。而**磁盘真实文件名是正确的**（目录列表显示 `寻迹.epub`）。

**结论：错误发生在"目录扫描 → 内存字符串"这一段**，不是显示层。

**修复方案（v1 必做）**
1. **统一入口**：SD 卡路径进入系统的**唯一**函数负责编码归一化 → 全固件内部**只用 UTF-8**。
2. **FAT 长文件名读取后立即验证**：用 `esp_rom` 的 UTF-16LE → UTF-8 转换，**不经过任何本地代码页**。禁止使用 `strncpy`/`printf("%s")` 之外的字节级操作改路径。
3. **加自检**：启动时扫描 3 个已知中文文件，比对"磁盘原始 UTF-16 名字"与"内存 UTF-8 名字"解码回 UTF-16 是否一致；不一致则在日志报 `PATHENC` 错误。
4. **加回归测试**（host 测试，不需要真机）：一组中文/日文/emoji 文件名 → 存进 `recent.json` → 读回 → 断言字节相同。**这正是 `read-pico-reader` 有 821 个 host 测试可以借鉴的地方。**
5. **一次性修复已有数据**：迁移时检测 `recent.json`/`state.json` 里的乱码条目，用**磁盘真实文件名重新生成**（因为真实文件名是对的），丢弃错误的旧值。

> 这一条是**本设计里优先级最高的单项工作**。它影响最近阅读、书库、进度恢复、KOReader 同步匹配——几乎是所有"书"的路径。

### 8.4 凭据与隐私

现状（`.crosspoint/wifi.json`）：
```json
{"ssid":"CU_74Kc",
 "password_obf":"canntTZxcqA=",     // Base64，8 字节 → 与 password_len:8 吻合
 "password_len":8,
 "password_crc32":4197220851}
```
`password_obf` 是 8 字节明文经过**简单可逆变换 + Base64**（长度与明文等长 → 大概率是 XOR 固定密钥或逐字节偏移，**不是加密**）。`password_crc32` 用于校验解码是否正确。

`read-pico-reader` 则更直接：**备份文件 `Pico-settings.backup` 里含明文 WiFi 密码**，README 自己提示"keep the TF card private"。

**纸读 v1 的决定**：
- **保持与 CrossMux 相同的混淆方式**（迁移无损、回退兼容）。
- 在设置页 WiFi 项加一句说明：「密码以可逆混淆存储，请勿转借 SD 卡」。**诚实标注比假安全更负责。**
- ✅ **微信读书相关风险整体消失**（决策 3）。原先最需要向用户明示的风险——上游自己文档里写的 `setInsecure()`（**不校验证书与主机名**）——随模块删除而**不复存在**。
  这是决策 3 最容易低估的收益：**纸读不再持有任何会向非官方服务器发送凭据的代码路径**。
- WiFi 凭据是唯一的落盘凭据。可选加固：给一个"用完即清"开关（传书完成后清除 WiFi 密码）。
- **不需要 SD 卡加密**，但 `settings.json` 不写入任何明文凭据。

## 附录 A：可直接使用的字体档位规划

> **正文默认字号 = 20pt（已定决策 1）**，因此内嵌字库的**主档位是 20pt**。

### A.1 内置（固件内嵌）—— 目标：不装 SD 字体即可完整读中文小说

| 档位 | 用途 | 覆盖范围 | **实测体积（压缩）** | 优先级 |
|---|---|---|---|---|
| **20pt** | **正文默认（主档位）** | GB2312 一二级（7,373 字形） | **1,153,378 B（1.13 MB）** | ⭐ **必做，不可降级** |
| **14pt** | 列表项、次级正文、设置项标题 | 同上 | **801,494 B（783 KB）** | ✅ 内嵌（已恢复） |
| **12pt** | 页脚、书库作者、设置副标题 | 同上 | **724,941 B（708 KB）** | ✅ 内嵌 |
| | | **三档合计** | **2,679,813 B（2.56 MB）** | ✅ 余约 3.35 MB 给固件 |

> ⚠️ **必须启用 `--compress`**。三档未压缩是 5.35 MB，会把预算吃光。
> 且**不要以 `.h` 文件体积判断**——位图存为十六进制文本，文件大小约为真实字节的 6 倍。

**降级顺序（已按实测重排，见 §6.4）**
```
① 先砍 12pt（页脚/副标题用 14pt 或 20pt 缩放）  → 省 724,941 B
② 再砍 14pt（列表项/设置标题走 SD 字库）        → 再省 801,494 B
③ 20pt 缩到 3500 常用字（不缩字号）              → 省约一半
```
> **为什么 20pt 排最后**：它是**正文**，用户明确指定，缩字号会直接伤害阅读体验；而 12/14pt 只影响页脚与列表，用户感知弱得多。



**其他说明**
- **字形来源**：**Noto Sans SC**（OFL-1.1，与上游一致，工具链现成）。
- **中文 UI 字重**：上游已说明**没有 CJK 粗体**，`EpdFontFamily::Style::Bold` 在中文下退化为常规 —— 纸读沿用，UI 里**不要依赖粗体做层级**，改用**字号 + 4 级灰 + 1px 分隔线 + 反白实心块**表达层级（§7.1 已论证）。
- **18 / 22 / 24pt 不内嵌**。用户已装 4 套 **8/10/12/14/16/18/20/22pt** 的 `.cpfont`，大字号从 SD 走即可——**而且 20pt 他自己就有**，这意味着内置 20pt 甚至可以在用户不装任何字体时就覆盖他当前的阅读习惯。


### A.2 SD 字体（用户自备）—— 保留现状，不加负担

| 项 | 处理 |
|---|---|
| 现有 4 套字体（LXGWWenKai Light / MiSans / QingNiaoHuaGuang / SanJiDianHei） | **完全兼容**，`.cpfont` 格式不变 |
| 目录约定 | `fonts/<家族名>/<家族名>_<size>.cpfont`（沿用；用户现有目录结构就是这个） |
| `LXGWWenKaiScreen.ttf` 直读 | ReadPico 有 PSRAM，支持 TTF 直读；设为可选（TTF 直读更慢但省 SD 空间） |
| 字体列表 UI | 显示「内置」分组 + 「SD 卡」分组；内置档位标注「完整中文」，SD 档位标注字号 |
| **移除** | 字体在线下载目录（`crossmux.cn`/`crossmux.com` 的 fonts.json）—— 内置已够用 |

### A.3 字体加载策略（内存安全）

```
常驻：当前正文字号档（1 个 family，1 个 size）
按需：UI 需要的档位（最多 3 个：12/14/16）
LRU：  ≥4 个档位被请求时，淘汰最久未用者

峰值 PSRAM 占用 = 1 正文档 + 3 UI 档 + glyph 缓存
         ≈ 300 KB + 3×80 KB + 1 MB(已有 glyph cache)   ← PSRAM 8 MB 完全够
内部 RAM 占用 = 仅索引与状态（<8 KB）                  ← 保护 30–45 KB 的紧张区
```

**上游已有的一个省时优化：把选中的 SD 字体缓存进"不活动的 OTA 槽"。**
`.cpfont` 首次从 SD 载入较慢。CrossMux 的做法是把选中的阅读字体**写进当前未运行的那个 A/B 应用槽**（槽前 4096 B 是 `CPSDFC1` 缓存头，其余最多 6,549,504 B 存 `.cpfont` 载荷），并由 OTA 流程在确认新固件后才回收该槽。**不修改 `otadata`，OTA 会自然覆盖它。**
**纸读沿用该机制**——它是"不花 Flash、又能大幅缩短字体载入"的唯一办法。配合 §1.5 的原子写入纪律（先擦头 → 写载荷 → CRC 校验 → 最后提交头）。

## 附录 D：字体封装格式对比（`TTF→BIN` vs `.cpfont`）—— 是否值得学 M5Stack

> 本节回应一个具体的工程提案：**是否采用 M5Stack 生态的"TTF 预栅格化成 .bin"方案**来替代/补充现有的 `.cpfont`。结论先说：**思路完全正确且值得借鉴，但不要直接换格式——两边的位深不同，换了会损失画质。**

### D.1 先澄清"M5Stack 的 TTF-to-BIN 工具"到底是什么

调研后需要做一处**重要的事实澄清**：被广泛转述的那个 TTF→BIN 工具，**不是 M5Stack 官方发布的通用字体工具**，而是第三方项目 `yuleshow/M5Stack-Paper-S3-Chinese-Books` 里的一个脚本：

| 项目 | 事实 |
|---|---|
| 脚本位置 | `scripts/convert_ttf_to_bin.py`（884 行，另带 GUI：`--gui`） |
| 所属仓库 | `yuleshow/M5Stack-Paper-S3-Chinese-Books`（17★，C，**GPL-2.0**，最后推送 2026-05-22） |
| 脚本自述 | *"Convert TTF font to **M5ReadPaper** binary format — Based on **M5ReadPaper's** font structure"* |
| 运行时渲染 | 该仓库**同时**依赖 `takkaO/OpenFontRender`（直接读 TTF 运行时渲染），并用 `scripts/patch_ofr_psram.py` 打补丁 |
| 官方 M5Stack 侧 | M5GFX/M5Unified 本身走的是 **LovyanGFX 的字体体系**（`lgfx_fonts`），另有 `LGFXFontToolJs` 之类的社区网页工具 |

**所以准确说法是**：「M5Stack 生态里有一个把 TTF 预栅格化为 `.bin` 的实践」，而**不是**「M5Stack 官方有一个 TTF-to-BIN 工具」。被转述时把来源归到了 M5Stack 品牌上。

> ⚠️ **许可证提醒**：`convert_ttf_to_bin.py` 所在仓库是 **GPL-2.0**。**不能把它的代码直接搬进纸读**（纸读基线是 MIT，GPL-2.0 会传染）。**可以借鉴格式设计与算法思路，代码必须自己写。** 这一点在采用前必须确认。

### D.2 该格式的真实二进制布局（已从源码逐字段核实）

**文件 = 137 字节头 + 20 字节/字的索引 + 位图数据块**（全部小端）：

```
偏移     字段                      类型        说明
─────────────────────────────────────────────────────────────────
== 头 137 字节 ==
0        char_count                uint32      字符数
4        font_size                 uint8       ⚠️ 只有 1 字节 → 最大 255
5        version                   uint32      = 2
9        family_name               char[64]    UTF-8，右侧 \0 补齐
73       style_name                char[64]    UTF-8，右侧 \0 补齐
─────────────────────────────────────────────────────────────────
== 索引 20 字节/字 ==
+0       unicode                   uint32      码点
+4       width                     uint16      位图宽（裁剪后）
+6       height                    uint16      位图高（裁剪后）
+8       offset                    uint32      位图数据的绝对文件偏移
+12      size                      uint32      该字位图字节数
+16      bearing_x                 int16       相对绘制原点的横向偏移
+18      bearing_y                 int16       相对绘制原点的纵向偏移
─────────────────────────────────────────────────────────────────
== 位图数据 ==
每个字：行主序、**每字节 8 像素、MSB 优先**、**1 bit/像素**、黑色=1
行按字节对齐 → 每字 size = ceil(width/8) * height
所有位图紧挨排列，无 padding、无压缩
```

**关键实现细节**（源码级）

- **栅格化用 Pillow**：`ImageDraw.textbbox()` 求内容外框 → 以 `font_size` 为安全原点绘制 → `img.crop(bbox)` 裁到实际墨迹 → 记录 `bearing_x/y` 相对原点。
- **⚠️ 位深是 1 bit，没有抗锯齿。** 源码写死 `Image.new('1', ...)`（1-bit 模式）。**这与本项目最关键的需求直接冲突**——见 D.3。
- **字形来源范围极广**：`get_common_chinese_chars()` 默认取 **U+4E00–U+9FFF 全块（20,992 字）** + CJK 标点/全角/竖排形式/通用标点/Latin-1/字母式符号/几何图形。即**它默认做的是"全汉字块"而不是子集**。
- **支持 fallback 字体**：主字体 cmap 里没有的字，从 `--fallback` 字体借用（用于补齐缺字）。
- **竖排支持是真做了**：把 `「」『』〈〉《》【】（）〖〗〔〕｛｝［］` 等横排括号**旋转 90°** 生成对应的竖排形式（`U+FE41`←`U+300C` …）；而 `︙︰︱︴` 等非括号项**不旋转**，只从 fallback 借用。→ 这是一个**繁体竖排/黄历场景**的专门需求，纸读 v1 用不到（本机是横排简体）。
- **`font_size` 只存 1 字节**，且这 1 字节存的是**实际渲染尺寸**（以便设备侧 `binScale = 1.0`）。其 `--size` 参数另有"名义尺寸 vs 渲染尺寸"的换算逻辑（Silver 字体有内置比例）。

### D.3 与现有 `.cpfont` v4 的正面对比

`.cpfont` 的结构（同样从源码核实）：

```
== 头 32 字节 ==
0    magic[8]   = "CPFONT\0\0"
8    version    uint16      = 4
10   flags      uint16      = 1   ← 注释写明 "always 2-bit greyscale"
12   styleCount uint8       （最多 4 种：regular/bold/italic/bold-italic）
13   reserved   uint8[19]
== 样式 TOC（每样式一条）==
     styleId(1) + pad(3) + intervalCount(4) + glyphCount(4) + ...
== 每样式的三段数据 ==
1) intervals：每区间 struct.pack("<III", start, end, glyphOffset)   ← 12 B/区间，不是 12 B/字！
2) glyphs   ：每字 GLYPH_STRUCT_FORMAT（含度量）
3) bitmaps  ：2-bit
附带 kerning（左右 class 对 + 矩阵）、连字（ligature）表
```

| 维度 | **M5Stack 生态的 TTF→BIN** | **`.cpfont` v4（纸读现状）** | 对纸读的判决 |
|---|---|---|---|
| **位深 / 抗锯齿** | **1 bit，无 AA** | **2 bit 灰度（4 阶）**；4-bit 栅格化后降采样 | ✅ **`.cpfont` 胜。** 墨水屏上 CJK 无 AA 会明显毛糙，尤其 12/14pt；本机面板支持 16 级灰，浪费它是倒退 |
| **码点→字形映射** | **20 B/字**，逐字一条 | **12 B/区间**（`start,end,offset`） | ✅ **`.cpfont` 大胜。** 6,763 字若连成少数区间，索引从 **135 KB 降到几 KB** |
| 每字形元数据 | 20 B（含 bearing，够用） | 有独立 glyph 表 + 字距 class | 平手偏 `.cpfont`（有 kerning/ligature） |
| 压缩 | 无 | 无 | 平手（都靠"预栅格化"而非压缩来省时） |
| 一个文件存多字号 | ❌ 一文件一尺寸 | ❌ 一文件一尺寸（`_8/_10/..._22` 命名） | 平手；与用户现有目录结构一致 |
| 一个文件存多种字重 | ❌ 只有 `style_name` 字符串 | ✅ 最多 4 种 style | ✅ `.cpfont` 胜 |
| 字号字段 | **uint8**（上限 255） | 无此字段（字号在文件名/metadata） | 平手（都用不到那么大） |
| 缺字回退 | ✅ `--fallback` 字体 | ⚠️ 运行期按"整串"回退到别的字体 | ✅ **TTF→BIN 思路胜**：**在构建期**补齐缺字比运行期换字体好。纸读应借鉴 |
| 竖排括号旋转 | ✅ 已实现 | 未见 | 纸读 v1 不需要（横排简体）；**若将来做竖排再借鉴** |
| 工具语言/易用性 | Python + **GUI 模式** | Python（`fontconvert_sdcard.py`，命令行 + 网页版） | 平手；两者都有 GUI 或网页封装 |
| 许可证 | **GPL-2.0**（不可直接搬代码） | MIT 生态 | ✅ `.cpfont` 无传染风险 |
| Flash 加速缓存 | ❌ 未见 | ✅ **可用非活动 OTA 槽缓存**（`CPSDFC1`） | ✅ `.cpfont` 胜 |

### D.4 结论与具体行动

**结论：值得学的是三点思路，不值得换的是格式本身。**

**✅ 应当借鉴（3 条）**

1. **"构建期预栅格化"这个大方向是对的，纸读已经在用**（`.cpfont` 就是预栅格化）。所以这个提案的核心判断**与现有方案一致**，不需要改路线——但**值得把它明确写进设计原则**："阅读字体一律预栅格化，运行期绝不解析 TTF"。
2. **构建期缺字回退（`--fallback`）——这是真正该抄的一条。** 现在 CrossMux 是"运行期发现缺字 → 整串换字体 → 弹窗引导下载完整字库"，体验很差。改成：**生成内置字库时，把主字体缺失的字从 fallback 字体补进来**（例如 Noto Sans SC 缺的符号从 Noto Sans Symbols 补）。这样"内置字库完整"就变成一个**构建期可验证的断言**，而不是运行期的运气。
   → 对应阶段 2 的新增验收项：**构建期生成"缺字报告"，断言用户书架里的书零缺字。**
3. **`--gui` 的可用性思路值得抄。** 给字库生成做一个 GUI/网页封装（CrossMux 网页版已有"SD-card font builder"，可扩展成支持任意 TTF + 任意区间 + 缺字回退 + 体积预估）。

**❌ 不应采纳（2 条）**

1. **不要把 `.cpfont` 换成该 `.bin` 格式。** 两个硬伤：**① 1-bit 无抗锯齿**（直接降低正文观感，本机面板明明支持 16 级灰）；**② 20 B/字的逐字索引**（6,763 字 = 135 KB 纯索引，而 `.cpfont` 的区间表只要几 KB）。在 Flash 只剩 419 KB、且字库是最大开支的项目里，这两条都是反向的。
2. **不要直接使用该脚本的代码**（GPL-2.0 会与纸读的 MIT 基线冲突）。要借鉴就**按 D.2 的布局自己实现**，或更好——**直接扩展现有的 `fontconvert_sdcard.py`**（MIT 生态，且已经支持 `cjk` 区间预设、4-bit→2-bit 降采样、kerning/ligature）。

| D-4 | 生成后打印 `区间数 / 字形数 / 索引字节 / 位图字节` 四项 | 让"每字 380 KB"从传说变成实测 |
| D-5 | 若将来做竖排，再借鉴 `VERT_BRACKETS_TO_HORIZ` 的括号旋转表 | 暂不实现 |
